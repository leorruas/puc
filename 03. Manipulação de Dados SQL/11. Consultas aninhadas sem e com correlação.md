# Consultas aninhadas sem e com correlação

> **Contexto:** Este artigo apresenta subconsultas — também chamadas de consultas aninhadas ou *subqueries* — e mostra como uma consulta pode usar o resultado de outra consulta. O foco está em subconsultas escalares, comparações com conjuntos, diferença entre subconsultas sem correlação e correlacionadas e uso de `EXISTS`.

Até aqui, as consultas foram construídas combinando filtros, agrupamentos e junções. Há situações, porém, em que uma pergunta depende primeiro da resposta de outra pergunta.

Por exemplo:

> quais produtos têm preço maior do que a média de todos os produtos?

Antes de decidir quais produtos mostrar, precisamos descobrir a média. Esse cálculo pode ser colocado dentro da própria consulta, formando uma **subconsulta**.

## 1. Modelo mental: uma consulta usa o resultado de outra

Uma subconsulta é um bloco `SELECT` escrito dentro de outra consulta SQL. A consulta mais externa é a **consulta externa**; a consulta inserida entre parênteses é a **subconsulta**, **consulta aninhada** ou **subquery**.

~~~sql
SELECT NomeProduto, Preco
FROM Produto
WHERE Preco > (
    SELECT AVG(Preco)
    FROM Produto
);
~~~

Podemos ler a instrução em duas etapas:

| Parte | Papel |
| --- | --- |
| `SELECT AVG(Preco) FROM Produto` | produz a média dos preços |
| consulta externa | compara cada produto com esse resultado |

O resultado da subconsulta existe durante a execução e pode assumir formatos diferentes:

| Forma do resultado | Uso típico |
| --- | --- |
| uma linha e uma coluna | comparação com `=`, `>`, `<` etc. |
| várias linhas e uma coluna | comparação com `IN`, `NOT IN`, `ANY` ou `ALL` |
| várias linhas e várias colunas | comparação ou composição compatível com esse formato |

Quando a subconsulta retorna um único valor, ela é chamada de **subconsulta escalar**:

~~~sql
SELECT customer_id, first_name, last_name
FROM customer
WHERE customer_id = (
    SELECT MAX(customer_id)
    FROM customer
);
~~~

## 2. Subconsultas sem correlação e comparação com conjuntos

Uma subconsulta é **sem correlação** quando não depende de nenhuma coluna da consulta externa. Ela pode ser entendida e executada isoladamente.

No exemplo da média geral:

~~~sql
SELECT AVG(Preco)
FROM Produto;
~~~

a consulta interna independe da linha que a consulta externa está examinando.

Quando o resultado é uma lista, podemos usar operadores que comparam a linha externa com esse conjunto:

| Operador | Ideia central |
| --- | --- |
| `IN` | o valor aparece no conjunto retornado |
| `NOT IN` | o valor não aparece no conjunto |
| `ANY` | a comparação é verdadeira para pelo menos um valor |
| `ALL` | a comparação precisa ser verdadeira para todos os valores |

**`IN` e `NOT IN`** trabalham com pertencimento. Para obter cidades do Canadá ou México:

~~~sql
SELECT city_id, city
FROM city
WHERE country_id IN (
    SELECT country_id
    FROM country
    WHERE country IN ('Canada', 'Mexico')
);
~~~

Para excluir essas cidades:

~~~sql
SELECT city_id, city
FROM city
WHERE country_id NOT IN (
    SELECT country_id
    FROM country
    WHERE country IN ('Canada', 'Mexico')
);
~~~

**`ALL`** exige que a comparação seja verdadeira em relação a todos os valores retornados:

~~~sql
SELECT first_name, last_name
FROM customer
WHERE customer_id <> ALL (
    SELECT customer_id
    FROM payment
    WHERE amount = 0
);
~~~

Nesse exemplo, a lógica é equivalente a `NOT IN`: o código do cliente precisa ser diferente de todos os códigos retornados.

**`ANY`** exige apenas que a comparação seja verdadeira para pelo menos um valor. Uma condição como:

~~~sql
HAVING SUM(amount) > ANY (
    SELECT SUM(p.amount)
    FROM payment AS p
    INNER JOIN customer AS c
        ON p.customer_id = c.customer_id
    INNER JOIN address AS a
        ON c.address_id = a.address_id
    INNER JOIN city AS ct
        ON a.city_id = ct.city_id
    INNER JOIN country AS co
        ON ct.country_id = co.country_id
    WHERE co.country IN ('Bolivia', 'Paraguay', 'Chile')
    GROUP BY co.country
);
~~~

pergunta se o total da consulta externa é maior do que **pelo menos um** dos totais produzidos pela subconsulta.

A diferença central é:

| Expressão | Condição de verdade |
| --- | --- |
| `> ANY (...)` | maior que pelo menos um valor |
| `> ALL (...)` | maior que todos os valores |

## 3. Subconsultas correlacionadas

Uma subconsulta é **correlacionada** quando referencia uma coluna da consulta externa.

Considere a pergunta:

> quais produtos têm preço menor do que a média de preço da própria categoria?

~~~sql
SELECT
    P.NomeProduto,
    P.Preco
FROM Produto AS P
WHERE P.Preco < (
    SELECT AVG(P2.Preco)
    FROM Produto AS P2
    WHERE P2.Categoria = P.Categoria
);
~~~

A correlação aparece em:

~~~sql
P2.Categoria = P.Categoria
~~~

`P2.Categoria` pertence à consulta interna. `P.Categoria` pertence à linha atual da consulta externa.

O modelo mental é linha a linha:

| Produto | Categoria | Preço |
| --- | --- | ---: |
| Computador AMD | 1 | 3500 |
| Computador Intel | 1 | 1000 |
| Impressora Epson | 2 | 1500 |
| Mouse | 3 | 80 |
| Mesa digitalizadora | 3 | 460 |

Para cada produto, podemos imaginar a sequência:

1. pegar a categoria da linha atual;
2. usar essa categoria dentro da subconsulta;
3. calcular a média daquela categoria;
4. comparar o preço do produto com a média;
5. manter a linha se a condição for verdadeira.

A consulta interna isolada:

~~~sql
SELECT AVG(P2.Preco)
FROM Produto AS P2
WHERE P2.Categoria = P.Categoria;
~~~

não funciona sozinha porque `P.Categoria` só existe no contexto da consulta externa.

A comparação entre os dois tipos fica assim:

| Tipo | Depende da consulta externa? | Pode ser executada isoladamente? |
| --- | --- | --- |
| sem correlação | não | sim |
| com correlação | sim | não, se usa referência externa |

Outro exemplo é contar ocorrências para cada cliente:

~~~sql
SELECT c.first_name, c.last_name
FROM customer AS c
WHERE 20 = (
    SELECT COUNT(*)
    FROM rental AS r
    WHERE r.customer_id = c.customer_id
);
~~~

A subconsulta conta os aluguéis do cliente da linha externa. Se a contagem for igual a 20, o cliente aparece.

## 4. `EXISTS`: testar existência, não quantidade

Há perguntas em que não precisamos saber quantas linhas existem nem qual valor elas contêm. Basta saber se existe ao menos uma ocorrência que satisfaça a condição.

~~~sql
SELECT c.first_name, c.last_name
FROM customer AS c
WHERE EXISTS (
    SELECT 1
    FROM rental AS r
    WHERE r.customer_id = c.customer_id
      AND DATE(r.rental_date) < '2005-05-25'
);
~~~

A pergunta é:

> existe pelo menos um aluguel desse cliente realizado antes de 25 de maio de 2005?

O `SELECT 1` não representa contagem. Em `EXISTS`, o valor selecionado não é a informação principal; interessa apenas saber se a subconsulta encontrou uma linha.

O mesmo padrão pode ser aplicado a produtos e fornecedores:

~~~sql
SELECT
    P.NomeProduto,
    P.Preco
FROM Produto AS P
WHERE EXISTS (
    SELECT 1
    FROM Fornecedor AS F
    WHERE F.CodigoFornecedor = P.Fornecedor
      AND F.Cidade LIKE 'Belo%'
);
~~~

Para cada produto, a subconsulta verifica se existe um fornecedor correspondente cuja cidade começa com `Belo`.

## 5. Como escolher a construção

Uma forma prática de escolher a estrutura é observar **o que a consulta interna precisa devolver e como a consulta externa vai usar esse resultado**.

| Pergunta | Construção útil |
| --- | --- |
| preciso de um único valor? | subconsulta escalar + operador de comparação |
| preciso saber se um valor pertence a uma lista? | `IN` |
| preciso garantir que não pertence à lista? | `NOT IN` |
| preciso comparar com pelo menos um valor? | `ANY` |
| preciso comparar com todos os valores? | `ALL` |
| só preciso saber se existe alguma linha? | `EXISTS` |
| a consulta interna precisa de um valor da linha externa? | subconsulta correlacionada |

Subconsulta e `JOIN` não são sinônimos. No [[10. Cláusula JOIN, junções e UNION|artigo 10]], `JOIN` aparece principalmente para combinar linhas de tabelas relacionadas. A subconsulta é útil quando uma parte da decisão depende do **resultado de outra consulta**. Uma subconsulta também pode conter `JOIN`, agrupamentos e outras construções.

O modelo mental é:

> **`JOIN` responde “como relaciono estas tabelas?”; a subconsulta responde “preciso usar o resultado de outra consulta dentro desta decisão?”.**

## 6. Script de prática

~~~sql
-- produtos com preço acima da média geral
SELECT NomeProduto, Preco
FROM Produto
WHERE Preco > (
    SELECT AVG(Preco)
    FROM Produto
);

-- cidades do Canadá ou México
SELECT city_id, city
FROM city
WHERE country_id IN (
    SELECT country_id
    FROM country
    WHERE country IN ('Canada', 'Mexico')
);

-- cidades fora do Canadá e México
SELECT city_id, city
FROM city
WHERE country_id NOT IN (
    SELECT country_id
    FROM country
    WHERE country IN ('Canada', 'Mexico')
);

-- comparação com ALL
SELECT first_name, last_name
FROM customer
WHERE customer_id <> ALL (
    SELECT customer_id
    FROM payment
    WHERE amount = 0
);

-- produto abaixo da média da própria categoria
SELECT
    P.NomeProduto,
    P.Preco
FROM Produto AS P
WHERE P.Preco < (
    SELECT AVG(P2.Preco)
    FROM Produto AS P2
    WHERE P2.Categoria = P.Categoria
);

-- cliente com exatamente 20 aluguéis
SELECT c.first_name, c.last_name
FROM customer AS c
WHERE 20 = (
    SELECT COUNT(*)
    FROM rental AS r
    WHERE r.customer_id = c.customer_id
);

-- cliente com pelo menos um aluguel antes da data indicada
SELECT c.first_name, c.last_name
FROM customer AS c
WHERE EXISTS (
    SELECT 1
    FROM rental AS r
    WHERE r.customer_id = c.customer_id
      AND DATE(r.rental_date) < '2005-05-25'
);

-- produtos de fornecedores cuja cidade começa com Belo
SELECT
    P.NomeProduto,
    P.Preco
FROM Produto AS P
WHERE EXISTS (
    SELECT 1
    FROM Fornecedor AS F
    WHERE F.CodigoFornecedor = P.Fornecedor
      AND F.Cidade LIKE 'Belo%'
);
~~~

## Pontos que costumam gerar confusão

- **A subconsulta participa da consulta maior.** Ela não é apenas um exemplo separado colocado dentro do código.
- **Subconsulta escalar precisa produzir um valor compatível com a comparação externa.**
- **`IN` e `NOT IN` trabalham com pertencimento a um conjunto.**
- **`ANY` exige pelo menos uma correspondência; `ALL`, todas.**
- **Uma subconsulta sem correlação não depende da linha externa.**
- **Uma subconsulta correlacionada usa uma referência da consulta externa.**
- **Aliases ajudam a distinguir a mesma tabela usada em níveis diferentes da consulta.**
- **`EXISTS` testa existência, não quantidade.**
- **`SELECT 1` dentro de `EXISTS` não significa “conte uma ocorrência”.**
- **Subconsultas podem conter `JOIN`, agregações e outras construções SQL.**
