# Comando `CREATE TABLE`

> **Contexto:** Este artigo introduz a criação de tabelas com `CREATE TABLE`, conectando a implementação do banco aos conceitos de entidades, atributos, chaves e cardinalidade estudados em [[02. Modelagem de Dados/00. Modelagem de Dados - Resumo|Modelagem de dados]]. Também diferencia conceitos transferíveis entre SGBDs de comandos e comportamentos específicos de sistemas como MySQL e SQL Server.

Depois de compreender o que é SQL e como um banco relacional organiza seus dados, o próximo passo é criar suas estruturas. O comando `CREATE TABLE` pertence à **DDL, Data Definition Language**, pois define a estrutura de uma tabela: seu nome, suas colunas, os tipos de dados dessas colunas e suas restrições.

Essa etapa materializa o modelo relacional. Aquilo que antes aparecia na modelagem como entidade, atributo, identificador e relacionamento passa a existir no SGBD como tabela, coluna, chave e restrição.

## 1. Da modelagem para a tabela

Quando um modelo apresenta uma entidade como **Fornecedor**, ela pode ser implementada como uma tabela. Seus atributos tornam-se colunas e o atributo escolhido para identificar unicamente cada ocorrência pode se tornar uma chave primária.

| Modelagem de dados | Implementação relacional |
| --- | --- |
| Entidade | Tabela |
| Atributo | Coluna |
| Identificador | Chave primária |
| Relacionamento | Chave estrangeira e restrições |
| Cardinalidade | Regras de relacionamento entre tabelas |

Em ferramentas gráficas de banco de dados, é comum aparecer um símbolo de chave ao lado de uma coluna. Esse símbolo indica que a coluna participa de uma chave, frequentemente a **chave primária** da tabela.

A cardinalidade estudada em Modelagem de dados não desaparece quando o banco é implementado. Ela será expressa por elementos como chaves estrangeiras, restrições de unicidade e pela própria organização das tabelas.

## 2. Estrutura básica de `CREATE TABLE`

Um comando de criação de tabela possui, de forma simplificada, esta estrutura:

```sql
CREATE TABLE NomeDaTabela (
    coluna1 TIPO restrições,
    coluna2 TIPO restrições
);
```

Dentro dos parênteses são declaradas as colunas que compõem a tabela. Cada coluna possui pelo menos um nome e um tipo de dado e também pode receber restrições.

Considere o exemplo:

```sql
CREATE TABLE Fornecedor (
    Codigo CHAR(3) PRIMARY KEY,
    Nome CHAR(20)
);
```

`Fornecedor` é o nome da nova tabela. `Codigo` e `Nome` são suas colunas.

### Lendo o comando

A primeira parte inicia a criação e determina o nome da tabela:

```sql
CREATE TABLE Fornecedor (
```

Em seguida, é definida a coluna `Codigo`:

```sql
Codigo CHAR(3) PRIMARY KEY,
```

`Codigo` é o nome da coluna, `CHAR(3)` é seu tipo e `PRIMARY KEY` determina que ela seja a chave primária.

A segunda coluna é definida como:

```sql
Nome CHAR(20)
```

Por fim:

```sql
);
```

o parêntese encerra a definição das colunas e o ponto e vírgula encerra a instrução SQL.

## 3. O que significa `CHAR`

`CHAR(n)` representa uma **cadeia de caracteres de comprimento fixo**. Portanto, dizer apenas que `CHAR` “aceita números e letras” é impreciso.

Por exemplo:

```sql
Codigo CHAR(3)
```

define uma coluna textual com três posições. Ela pode armazenar valores como `A01`, `123` ou `XYZ`, desde que sejam tratados como texto e respeitem o tamanho definido.

Mesmo quando o conteúdo é `123`, ele continua sendo tratado como texto, e não como o número inteiro 123. Essa diferença é importante porque textos e números possuem comportamentos diferentes para operações matemáticas, ordenação, validação e conversão.

Para textos cujo comprimento varia, muitos SGBDs oferecem o tipo `VARCHAR(n)`. Como modelo mental inicial: **`CHAR` = tamanho fixo** e **`VARCHAR` = tamanho variável até determinado limite**.

## 4. Chave primária

`PRIMARY KEY` define a chave primária da tabela. Ela garante que cada linha possa ser identificada de maneira única.

No exemplo:

```sql
Codigo CHAR(3) PRIMARY KEY
```

não podem existir dois fornecedores com o mesmo código. Além disso, uma chave primária não pode possuir valor nulo.

Uma analogia é o número de matrícula de um estudante. Pessoas diferentes podem ter o mesmo nome, mas a matrícula deve identificar um estudante específico sem ambiguidade.

A chave também pode ser declarada separadamente:

```sql
CREATE TABLE Fornecedor (
    Codigo CHAR(3),
    Nome CHAR(20),
    PRIMARY KEY (Codigo)
);
```

Quando a chave possui apenas uma coluna, as duas formas expressam essencialmente a mesma restrição. A segunda forma também será útil quando aparecerem chaves compostas.

## 5. Criando e selecionando um banco de dados

Primeiro, pode ser criado um banco chamado `ComercioTI`:

```sql
-- criação do banco de dados
CREATE DATABASE ComercioTI;
```

Em seguida:

```sql
USE ComercioTI;
```

seleciona esse banco como contexto para as instruções seguintes. Depois disso, pode ser criada a tabela `Fornecedor`.

É importante separar essas operações: `CREATE DATABASE` cria o banco, `USE` seleciona o banco corrente e `CREATE TABLE` cria uma tabela dentro desse contexto.

### Database e schema no MySQL

No MySQL, `DATABASE` e `SCHEMA` são usados como sinônimos nesse contexto. Assim, `CREATE DATABASE ComercioTI;` e `CREATE SCHEMA ComercioTI;` representam a mesma operação no MySQL.

Essa equivalência não deve ser generalizada para todos os SGBDs. Outros sistemas podem distinguir banco de dados e schema de maneira diferente.

Objetos como `livraria` podem aparecer na ferramenta como schemas ou databases. Já `sys` é um schema fornecido pelo próprio MySQL, que contém objetos voltados principalmente a informações operacionais e diagnóstico do servidor.

## 6. Comentários em SQL

Comentários de uma linha podem ser escritos utilizando dois hífens:

```sql
-- criação do banco de dados
CREATE DATABASE ComercioTI;
```

O conteúdo iniciado por `--` serve para documentar o código e não é interpretado como uma instrução a ser executada.

Também é comum o uso de comentários em bloco:

```sql
/*
Este trecho cria
a tabela Fornecedor.
*/
```

## 7. O ponto e vírgula

O ponto e vírgula não precisa aparecer ao final de **cada linha**. Ele é utilizado para encerrar uma **instrução SQL**.

Esta instrução, por exemplo, ocupa várias linhas:

```sql
CREATE TABLE Fornecedor (
    Codigo CHAR(3) PRIMARY KEY,
    Nome CHAR(20)
);
```

Existe apenas um `;`, porque existe apenas uma instrução completa. A utilização obrigatória ou tolerância à ausência do terminador pode variar conforme SGBD e ferramenta. Por consistência e portabilidade, é uma boa prática escrever as instruções completas com `;`.

## 8. Escrever não é o mesmo que executar

Digitar SQL no editor não modifica automaticamente o banco de dados. É necessário **executar** a instrução por meio do cliente utilizado.

O fluxo pode ser entendido assim: **escrever a instrução → executar no cliente → cliente envia ao SGBD → SGBD interpreta e valida → operação é realizada ou um erro é devolvido**.

DBeaver, MySQL Workbench, VS Code com extensões de banco de dados e outros clientes oferecem um botão ou atalho para execução. Escrever a instrução no editor não produz efeito até que ela seja efetivamente enviada ao SGBD para execução.

## 9. Maiúsculas e minúsculas

`CREATE TABLE Categoria` e `create table Categoria` normalmente têm o mesmo significado. A escrita das palavras-chave em maiúsculas é principalmente uma **convenção de legibilidade**.

Ela ajuda visualmente a separar palavras-chave da linguagem dos nomes escolhidos pelo desenvolvedor. A sensibilidade a maiúsculas e minúsculas de nomes de bancos, tabelas e outros objetos não deve ser inferida a partir disso, pois pode variar conforme o SGBD, configuração e sistema operacional.

## 10. Tipos de dados e diferenças entre SGBDs

Embora exista um padrão SQL, os tipos de dados implementados pelos SGBDs podem possuir nomes, limites e comportamentos diferentes. Por isso, ao trabalhar com um SGBD específico, também é necessário consultar a documentação de seus tipos.

Para comparar os tipos implementados por diferentes SGBDs com o padrão ANSI, podem ser consultadas estas referências:

- [Microsoft SQL Server](https://docs.microsoft.com/pt-br/office/client-developer/access/desktop-database-reference/equivalent-ansi-sql-data-types)
- [Oracle](https://docs.oracle.com/cd/E11882_01/server.112/e41084/sql_elements001.htm#SQLRF00213)

O modelo mental importante é separar **conceito** de **implementação específica**. Tabela, coluna, tipo e chave primária são conceitos gerais do modelo relacional e de SQL; os nomes exatos de determinados tipos e alguns detalhes da sintaxe podem mudar entre SGBDs.

## 11. Do diagrama à implementação

`CREATE TABLE` começa a transformar a modelagem estudada anteriormente em código executável. A sequência pode ser pensada assim: **entidade → tabela → atributos → colunas → identificador → chave primária → relacionamentos → chaves estrangeiras**.

Se o modelo possui `Fornecedor`, `Categoria` e `Produto`, cada uma dessas entidades pode dar origem a uma tabela. As relações entre elas, antes representadas por cardinalidades, serão posteriormente implementadas por chaves estrangeiras e outras restrições.

Portanto, o diagrama não é abandonado quando SQL começa. Ele funciona como um projeto da estrutura que será criada no banco.

## Pontos que costumam gerar confusão

- **`CHAR(3)` não significa “campo que aceita letras e números”.** Significa uma cadeia de caracteres de comprimento fixo com três posições.
- **O ponto e vírgula encerra a instrução, não cada linha.** Uma instrução SQL pode ocupar várias linhas.
- **`PRIMARY KEY` não é apenas o desenho de uma chave na interface.** É uma restrição que garante identificação única das linhas.
- **`CREATE DATABASE`, `USE` e `CREATE TABLE` não representam a mesma operação.** Respectivamente, criam o banco, selecionam o contexto e criam uma tabela.
- **Database e schema não são sempre sinônimos.** No MySQL são tratados como equivalentes nesse contexto, mas isso varia entre SGBDs.
- **Maiúsculas em `CREATE TABLE` são principalmente uma convenção de legibilidade.**
- **Modelagem e SQL não são etapas desconectadas.** `CREATE TABLE` transforma decisões do modelo relacional em estruturas reais.
