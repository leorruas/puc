# Bancos de dados relacionais e SGBDs

> **Contexto:** Este artigo retoma a estrutura dos bancos de dados relacionais para mostrar sobre o que SQL realmente opera. O foco está em relações, tuplas, atributos, domínios, chaves, restrições e no papel do SGBD como servidor acessado por clientes como terminal, DBeaver ou VS Code. A leitura também diferencia o sentido de **domínio** no modelo relacional do sentido usado em [[05. Desenvolvimento Web Back-End/01. Arquitetura de software e cliente-servidor#O que é domínio|Desenvolvimento Web Back-End]].

SQL é uma linguagem de comunicação com bancos de dados relacionais. Para utilizá-la com segurança, é necessário reconhecer a estrutura sobre a qual seus comandos atuam e separar conceitos que, no uso cotidiano, às vezes aparecem misturados: banco de dados, SGBD, servidor, cliente e ferramenta gráfica.

Este artigo retoma conceitos já estudados em [[02. Modelagem de Dados/00. Modelagem de Dados - Resumo|Modelagem de dados]], mas com um objetivo mais operacional. Na modelagem, a questão principal era como representar e estruturar os dados. Aqui, interessa entender como essa estrutura aparece dentro de um SGBD real e como passamos a interagir com ela por SQL.

## Estrutura de um banco de dados relacional

Um **banco de dados relacional** organiza os dados principalmente em **relações**, representadas na prática por tabelas. Cada tabela reúne ocorrências de algum objeto, evento ou associação relevante para o sistema.

Uma tabela de clientes poderia ser representada assim:

| id_cliente | nome | cidade |
| --- | --- | --- |
| 1 | Ana | Belo Horizonte |
| 2 | Bruno | Contagem |
| 3 | Carla | Belo Horizonte |

No vocabulário do modelo relacional, uma **relação** corresponde conceitualmente à estrutura representada por uma tabela; uma **tupla** corresponde a uma linha; um **atributo** corresponde a uma coluna; e um **domínio** define o conjunto de valores válidos que um atributo pode assumir. No uso cotidiano de SQL e das ferramentas de banco de dados, é mais comum falar em tabela, linha e coluna, mas os termos formais ajudam a compreender a lógica do modelo.

### Tipos de dados, domínios e restrições

Cada coluna possui uma definição que informa ao SGBD qual tipo de valor deve ser armazenado. Uma estrutura simples poderia ter:

| Coluna | Tipo esperado |
| --- | --- |
| `id_cliente` | número inteiro |
| `nome` | texto |
| `data_nascimento` | data |
| `ativo` | valor lógico |

O **tipo de dado** descreve a natureza geral do valor. O **domínio**, no sentido do modelo relacional, é mais específico: corresponde ao conjunto de valores considerados válidos para determinado atributo. Uma coluna `idade`, por exemplo, pode ter tipo inteiro, mas seu domínio pode excluir números negativos por meio de regras adicionais.

Essa distinção fica mais clara quando pensamos em uma nota de avaliação. O tipo poderia ser inteiro, mas o domínio válido poderia ser apenas `1`, `2`, `3`, `4` e `5`. Em SQL, parte dessas regras pode ser implementada por restrições como `CHECK`.

### A palavra domínio muda de sentido em Web Back-End

**Domínio** é uma palavra usada em mais de um contexto da computação, e os sentidos não devem ser confundidos.

| Contexto | Significado de domínio | Exemplo |
| --- | --- | --- |
| **Modelo relacional** | Conjunto de valores válidos que um atributo pode assumir | O atributo `nota` aceita apenas valores de 1 a 5 |
| **Arquitetura e Web Back-End** | Área de problema que o software precisa compreender, incluindo conceitos, regras e operações | Em um sistema de mentorias, mentor, estudante, agendamento e regras de disponibilidade fazem parte do domínio |

Assim, o **domínio relacional** é uma propriedade ligada aos valores possíveis de um atributo. O **domínio da aplicação** ou **domínio do negócio** é o universo do problema que o sistema representa. Os dois conceitos podem se encontrar: uma regra do domínio da aplicação pode ser traduzida para uma restrição que limita o domínio de um atributo no banco.

Por exemplo, se a regra de negócio diz que uma avaliação deve receber nota de 1 a 5, essa regra pode chegar ao banco como uma restrição sobre a coluna `nota`:

```sql
CHECK (nota BETWEEN 1 AND 5)
```

A explicação do outro sentido de domínio está em [[05. Desenvolvimento Web Back-End/01. Arquitetura de software e cliente-servidor#O que é domínio|O que é domínio, em Desenvolvimento Web Back-End]].

### Chaves e relacionamentos

O modelo relacional permite distribuir informações em tabelas diferentes e relacioná-las por meio de **chaves**. A **chave primária** identifica de maneira única cada linha de uma tabela. Em `Cliente`, por exemplo, `id_cliente` pode exercer esse papel.

Uma **chave estrangeira** referencia uma chave existente em outra tabela. Considere uma tabela `Pedido`:

| id_pedido | data | id_cliente |
| --- | --- | --- |
| 101 | 2026-09-17 | 1 |
| 102 | 2026-09-17 | 3 |

A coluna `id_cliente` em `Pedido` pode referenciar `Cliente.id_cliente`. Dessa forma, o banco representa que cada pedido pertence a determinado cliente sem repetir todas as informações do cliente em cada pedido. Essa estrutura será especialmente importante quando estudarmos `JOIN`, porque SQL poderá combinar dados de relações diferentes usando essas referências.

### Integridade dos dados

Um banco relacional também utiliza **restrições**, ou *constraints*, para impedir estados inválidos. Entre as mais comuns estão:

- `PRIMARY KEY`: identifica unicamente os registros;
- `FOREIGN KEY`: estabelece referências entre tabelas;
- `NOT NULL`: impede ausência de valor em determinada coluna;
- `UNIQUE`: impede repetição de valores em uma coluna ou conjunto de colunas;
- `CHECK`: restringe valores conforme uma condição.

Essas regras ajudam a preservar a **integridade dos dados**. Em vez de depender apenas da aplicação que acessa o banco, o próprio SGBD pode recusar operações que violem restrições definidas na estrutura.

## Banco de dados, SGBD, servidor e cliente

Banco de dados, SGBD e SQL representam coisas diferentes. O **banco de dados** é o conjunto organizado de estruturas e dados. O **SGBD** é o software responsável por criar, armazenar, consultar, alterar, proteger e administrar bancos. **SQL** é a linguagem usada para enviar instruções a esses sistemas.

Uma forma simples de separar os conceitos é:

| Elemento | Papel |
| --- | --- |
| **Banco de dados** | Contém estruturas e dados |
| **SGBD** | Gerencia os bancos e executa operações sobre eles |
| **SQL** | Expressa instruções para o SGBD |
| **Servidor** | Processo do SGBD que recebe e processa conexões |
| **Cliente** | Programa ou aplicação que se conecta ao servidor |

PostgreSQL, MySQL e Microsoft SQL Server são exemplos de SGBDs relacionais. Eles entendem SQL, embora cada um possua recursos e dialetos próprios.

### Uma analogia para separar as peças

Uma analogia possível é pensar em um arquivo organizado. O **banco de dados** é o acervo guardado; o **SGBD** é o sistema que sabe onde cada informação está, aplica regras e controla quem pode acessá-la; **SQL** é a linguagem usada para fazer pedidos a esse sistema; e DBeaver, terminal ou uma aplicação são os meios pelos quais esses pedidos chegam ao servidor. A analogia é limitada, mas ajuda a evitar a ideia de que banco, SGBD, SQL e cliente sejam a mesma coisa.

### Alguns SGBDs relacionais

**PostgreSQL** é um SGBD relacional de código aberto disponível em diferentes sistemas operacionais e com recursos que vão além do núcleo padronizado de SQL.

**MySQL** também é amplamente utilizado. A **MySQL Community Edition** é gratuita e adequada para aprendizagem e desenvolvimento, sendo uma das opções indicadas na disciplina.

**Microsoft SQL Server** possui edições comerciais e gratuitas. A edição **Developer** é voltada a desenvolvimento e testes; a edição **Express** é gratuita e possui limitações de recursos. É importante separar licença de compatibilidade: o mecanismo do SQL Server não possui instalação nativa suportada para macOS.

Em macOS, inclusive em Macs com Apple Silicon, é possível trabalhar com SQL Server usando a extensão oficial MSSQL do Visual Studio Code. Ela permite conectar-se a instâncias remotas e também criar e utilizar uma instância local em contêiner com Docker Desktop. A ressalva é que as imagens oficiais do SQL Server têm suporte formal apenas em hosts Linux x86-64; em Apple Silicon, a execução do contêiner depende de emulação e não é oficialmente testada nem suportada pela Microsoft.

## O SGBD como serviço do sistema operacional

Um SGBD precisa continuar disponível mesmo quando nenhuma interface gráfica está aberta. Por isso, o processo servidor normalmente funciona **em segundo plano**, como um serviço do sistema operacional. Fechar DBeaver ou o terminal não significa necessariamente desligar o banco: o cliente pode ser encerrado enquanto o servidor continua ativo.

No Windows, serviços podem ser inspecionados pela ferramenta de gerenciamento de serviços, onde processos aparecem com estados como `Running` ou `Stopped`. No macOS existe o mesmo conceito de processos e serviços em segundo plano, mas não há uma interface idêntica ao `services.msc`. Dependendo da instalação, o estado pode ser consultado pelo Monitor de Atividade, pelo `launchctl`, por ferramentas do próprio fornecedor ou, quando o SGBD foi instalado pelo Homebrew, com:

```bash
brew services list
```

A ideia central é independente do sistema operacional: existe um processo servidor que precisa estar ativo para aceitar conexões.

### Arquitetura cliente-servidor

O funcionamento pode ser entendido pela separação entre **cliente** e **servidor**. O cliente envia uma instrução SQL; o SGBD autentica a conexão, verifica permissões, interpreta a instrução, escolhe uma estratégia de execução, acessa os dados e devolve o resultado.

| Papel | Exemplos | Responsabilidade |
| --- | --- | --- |
| **Cliente** | terminal `mysql`, DBeaver, VS Code, aplicação Web | Abrir conexão e enviar comandos |
| **Servidor** | processo do MySQL, PostgreSQL ou SQL Server | Processar comandos e administrar os bancos |
| **Banco de dados** | tabelas, relações, índices, restrições e dados | Manter a informação persistida |

Cliente e servidor podem estar no mesmo computador ou em máquinas diferentes. Isso explica, por exemplo, por que DBeaver instalado no macOS pode acessar um SQL Server executado em outro ambiente.

## Como acessar um SGBD

Existem duas formas comuns de interação direta durante o estudo: clientes de linha de comando e ferramentas gráficas.

### Linha de comando

Muitos SGBDs fornecem clientes próprios de terminal. No MySQL, o comando `mysql` pode abrir uma sessão com o servidor:

```bash
mysql -u root -p
```

Nesse exemplo, `-u root` informa o usuário e `-p` solicita a senha. Depois da autenticação, o programa cliente envia os comandos digitados para o processo servidor. A linha de comando torna clara a distinção entre as partes: o executável `mysql` é o cliente, enquanto o MySQL Server é o SGBD que recebe e processa as instruções.

### Clientes gráficos e IDEs de banco de dados

Também é possível acessar SGBDs por interfaces gráficas que permitem criar conexões, navegar por objetos do banco, examinar tabelas e colunas, escrever consultas e visualizar resultados. Muitas vezes essas ferramentas são chamadas genericamente de **IDEs de banco de dados**, embora **cliente gráfico** ou **ferramenta de gerenciamento de banco de dados** seja uma descrição mais precisa para várias delas.

Uma conexão normalmente exige informações como SGBD, endereço do servidor ou *host*, porta, banco ou esquema, usuário, senha e método de autenticação. Depois da conexão, a interface pode apresentar bancos, esquemas, tabelas, *views*, índices e outros objetos.

### DBeaver

**DBeaver** é um cliente gráfico de banco de dados que suporta diferentes SGBDs. A edição Community é gratuita, e a ferramenta possui versões para Windows, Linux e macOS. Ela usa **drivers** para traduzir as operações do cliente para o protocolo e as particularidades de cada banco.

Ao criar uma conexão, escolhemos o SGBD e informamos os parâmetros necessários. MySQL, por exemplo, usa normalmente a porta `3306`; SQL Server usa normalmente a porta `1433`. Depois da conexão, o navegador de objetos permite examinar tabelas, colunas, chaves, restrições e outros metadados.

A vantagem didática do DBeaver é manter uma interface semelhante enquanto o SGBD muda. Assim, é possível praticar MySQL, PostgreSQL e SQL Server sem confundir a ferramenta usada para acessar o banco com o próprio banco.

### Ferramentas para SQL Server

No Windows, a ferramenta tradicional da Microsoft para administração do SQL Server é o **SQL Server Management Studio, SSMS**. Ele não possui versão para macOS.

No macOS, o **Visual Studio Code com a extensão oficial MSSQL** permite conectar-se a SQL Server e Azure SQL e executar consultas T-SQL. DBeaver também pode desempenhar esse papel de cliente. O **Azure Data Studio**, que aparece em materiais e tutoriais mais antigos, foi descontinuado pela Microsoft em 28 de fevereiro de 2026; a recomendação atual é migrar para o Visual Studio Code com a extensão MSSQL.

## O que aparece ao explorar uma tabela

Quando abrimos uma tabela em um cliente gráfico, a ferramenta consulta os **metadados** mantidos pelo SGBD. A interface pode mostrar nome das colunas, tipos de dados, tamanhos ou precisão, possibilidade de valores nulos, chaves primárias e estrangeiras, índices, valores padrão e demais restrições.

Essas informações descrevem a **estrutura** da tabela. Em outra área da ferramenta, podemos visualizar ou consultar o **conteúdo** armazenado nela. Essa separação prepara a distinção vista no artigo anterior: comandos de DDL atuam principalmente sobre estruturas, enquanto comandos de manipulação e consulta atuam sobre os dados que ocupam essas estruturas.

## Ponte com modelagem de dados

A passagem entre as disciplinas pode ser pensada como **modelo conceitual → modelo lógico relacional → implementação no SGBD → manipulação por SQL**. Na modelagem, definimos entidades, atributos, relacionamentos, chaves e regras; no SGBD, essas decisões aparecem concretamente como tabelas, colunas, restrições e referências; com SQL, passamos a criar, consultar e modificar essa implementação.

Por isso, uma tabela vista no DBeaver não representa um assunto separado da modelagem. Ela é a implementação concreta de decisões que antes apareciam em modelos e diagramas.

## Pontos que costumam gerar confusão

- **Banco de dados e SGBD não são sinônimos.** O banco contém estruturas e dados; o SGBD é o software que os administra.
- **SQL não é um SGBD.** SQL é a linguagem usada para expressar instruções que o SGBD executa.
- **Domínio relacional e domínio da aplicação são conceitos diferentes.** No modelo relacional, domínio limita os valores de um atributo; em Web Back-End, domínio representa a área de problema e suas regras.
- **DBeaver não é o servidor do banco.** Ele é um cliente que se conecta a um SGBD.
- **Fechar o cliente não necessariamente desliga o banco.** Se o SGBD estiver executando como serviço, ele pode continuar ativo em segundo plano.
- **SQL Server gratuito não significa SQL Server nativo em qualquer sistema operacional.** Licença e compatibilidade de plataforma são questões diferentes.
- **Uma ferramenta gráfica não substitui SQL.** Ela oferece uma interface para navegar e administrar o banco, mas as consultas continuam sendo expressas por SQL.
