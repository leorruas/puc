# Transações em banco de dados, `COMMIT` e `ROLLBACK`

> **Contexto:** Este artigo introduz transações como unidades lógicas de trabalho em bancos de dados, especialmente em ambientes multiusuário. O foco está em compreender como operações SQL já conhecidas podem ser agrupadas em uma única ação, efetivadas com `COMMIT` ou desfeitas com `ROLLBACK`, além da relação entre transações, concorrência, propriedades ACID e mecanismos internos de recuperação do SGBD.

Em sistemas reais, várias pessoas e aplicações podem acessar o mesmo banco ao mesmo tempo. Uma aplicação pode atualizar estoque, outra registrar uma venda, outra reservar uma viagem e outra transferir dinheiro entre contas. O SGBD precisa coordenar essas leituras e escritas de forma confiável, e as **transações** são uma das estruturas centrais para isso.

## Transação, unidade lógica e atomicidade

Uma transação é uma **unidade lógica de trabalho** formada por uma ou mais operações relacionadas entre si. Essas operações podem envolver inserção, exclusão, atualização ou consulta de dados, mas o ponto principal é que o conjunto represente uma única ação coerente do ponto de vista do negócio.

Uma transferência de R$ 100 entre duas contas mostra bem essa ideia: é necessário retirar R$ 100 da conta de origem e acrescentar R$ 100 à conta de destino. Se apenas o débito acontecer e o crédito falhar, a transferência não foi concluída corretamente. As duas alterações pertencem, portanto, à mesma unidade lógica.

A indivisibilidade dessa unidade corresponde à **atomicidade**:

> **Ou todas as operações da transação são efetivadas, ou nenhuma delas deve permanecer efetivada.**

Se uma falha ocorrer entre o débito e o crédito, por erro em uma instrução, falha no servidor, queda de energia, problema de disco ou outra interrupção, as alterações parciais precisam ser desfeitas. Isso evita um estado incoerente como:

```text
Conta A: -100
Conta B: +0
```

quando o resultado esperado era:

```text
Conta A: -100
Conta B: +100
```

Uma transação pode conter apenas uma instrução, mas seu valor fica mais evidente quando várias instruções precisam funcionar juntas. Uma atualização isolada:

```sql
UPDATE Conta
SET Saldo = Saldo - 100
WHERE Numero = 123;
```

é diferente de uma unidade lógica explícita:

```sql
BEGIN TRANSACTION;

UPDATE Conta
SET Saldo = Saldo - 100
WHERE Numero = 123;

UPDATE Conta
SET Saldo = Saldo + 100
WHERE Numero = 456;

COMMIT;
```

No segundo caso, as duas atualizações representam uma única ação de negócio.

**O que muda em relação aos comandos já estudados?**

Os comandos usados dentro de uma transação são, em grande parte, os mesmos vistos anteriormente. `INSERT`, `UPDATE` e `DELETE` continuam inserindo, alterando e excluindo registros. Um `SELECT` também pode ser executado dentro de uma transação. O assunto novo não é uma nova forma de manipular os dados, mas **como o SGBD trata várias operações como uma única unidade de trabalho**.

Isso cria uma distinção importante entre duas camadas:

- os comandos DML dizem **o que fazer com os dados**;
- os comandos de controle transacional dizem **quando considerar essas alterações confirmadas ou quando desfazê-las**.

Em muitos SGBDs, inclusive nas configurações usuais de SQL Server e MySQL, existe o modo de **autocommit**: quando não se abre uma transação explicitamente, cada instrução de alteração pode ser tratada como uma transação individual e confirmada automaticamente. Ao usar `BEGIN TRANSACTION` ou `START TRANSACTION`, várias instruções podem permanecer dentro da mesma unidade lógica até um `COMMIT` ou `ROLLBACK`.

Essa é a principal diferença conceitual deste conteúdo em relação aos comandos estudados anteriormente.

## Ciclo da transação: iniciar, confirmar ou desfazer

Uma transação possui três momentos conceituais: **início**, **execução das operações** e **encerramento**. O encerramento pode confirmar ou cancelar o que foi feito.

No SQL Server, a abertura explícita pode ser feita com:

```sql
BEGIN TRANSACTION;
```

No MySQL, a forma utilizada é:

```sql
START TRANSACTION;
```

O conceito é o mesmo, mas a sintaxe de início varia entre os dialetos.

Depois de executar as instruções da unidade de trabalho, existem dois caminhos principais:

| Comando | Função |
| --- | --- |
| `COMMIT` | confirma as alterações e encerra a transação com sucesso |
| `ROLLBACK` | desfaz as alterações ainda não confirmadas e encerra a transação |

Por exemplo, uma inserção confirmada:

```sql
BEGIN TRANSACTION;

INSERT INTO Produto (Codigo, Nome, Preco)
VALUES (100, 'Teclado mecânico', 300);

COMMIT;
```

faz com que a inclusão seja efetivada. Já:

```sql
BEGIN TRANSACTION;

INSERT INTO Produto (Codigo, Nome, Preco)
VALUES (100, 'Teclado mecânico', 300);

ROLLBACK;
```

desfaz a inclusão antes da confirmação.

O mesmo princípio vale para exclusões:

```sql
BEGIN TRANSACTION;

DELETE FROM Produto
WHERE Codigo = 100;

ROLLBACK;
```

Para a própria transação, a linha deixa de aparecer depois do `DELETE`, mas a exclusão ainda pode ser desfeita pelo `ROLLBACK`. A forma como outras transações enxergam essa alteração antes do `COMMIT` depende dos mecanismos e do nível de isolamento adotado pelo SGBD.

Se a intenção for confirmar a exclusão:

```sql
BEGIN TRANSACTION;

DELETE FROM Produto
WHERE Codigo = 100;

COMMIT;
```

Isso se conecta diretamente ao cuidado com `DELETE` discutido em [[05. Comandos INSERT, UPDATE e DELETE#Exclusão de dados com `DELETE`|INSERT, UPDATE e DELETE]].

## Aplicando transações a operações de negócio

A utilidade de uma transação aparece quando várias instruções representam uma única ação que não pode ficar incompleta.

Na transferência bancária:

```sql
BEGIN TRANSACTION;

UPDATE Conta
SET Saldo = Saldo - 100
WHERE Numero = 123;

UPDATE Conta
SET Saldo = Saldo + 100
WHERE Numero = 456;

COMMIT;
```

a intenção é que as duas atualizações sejam confirmadas juntas. Se algum erro impedir a segunda operação, a transação deve seguir o caminho de desfazer as alterações:

```sql
ROLLBACK;
```

A mesma lógica pode ser aplicada a outras situações, como registrar uma venda e atualizar estoque, inserir dados relacionados em mais de uma tabela ou cancelar alterações experimentais antes de confirmá-las.

Uma forma útil de raciocinar é:

1. iniciar a transação;
2. executar as operações relacionadas;
3. verificar se todas puderam ser concluídas;
4. usar `COMMIT` se tudo deu certo;
5. usar `ROLLBACK` se a unidade de trabalho precisar ser desfeita.

## Log, concorrência e propriedades ACID

Para conseguir confirmar, desfazer e recuperar operações depois de falhas, SGBDs transacionais mantêm **registros internos das alterações realizadas**. É comum chamar esse mecanismo, de forma geral, de **log de transações**.

Isso não significa que o SGBD simplesmente guarde uma cópia textual de cada comando SQL executado. O log normalmente registra informações internas suficientes para reconstruir ou desfazer alterações, e a implementação varia entre os sistemas.

No **SQL Server**, cada banco possui um transaction log que registra as transações e as modificações feitas por elas. Ele é usado, entre outras funções, para desfazer transações incompletas e recuperar o banco depois de uma falha. O SQL Server utiliza a estratégia de *write-ahead logging* (WAL): o registro correspondente à alteração é persistido no log antes que a página modificada seja gravada definitivamente no arquivo de dados.

No **MySQL com InnoDB**, a ideia aparece por meio de mecanismos como **redo log** e **undo log**. O redo log permite reaplicar alterações necessárias durante a recuperação depois de uma falha, enquanto informações de undo permitem reconstruir versões anteriores dos registros e desfazer alterações quando necessário.

Uma consequência importante é que **log de transações não é a mesma coisa que log de auditoria**. O primeiro existe principalmente para garantir recuperação, consistência e durabilidade interna do banco. Um log de auditoria, por outro lado, é pensado para responder perguntas como quem alterou determinado dado, quando isso ocorreu e qual ação foi executada.

**Concorrência e propriedades ACID.**

Em um ambiente multiusuário, diferentes aplicações podem executar operações de leitura e escrita simultaneamente sobre os mesmos dados. Nesse cenário, não basta conseguir usar `ROLLBACK` quando ocorre uma falha. O SGBD também precisa impedir que transações concorrentes produzam resultados incorretos.

Imagine duas pessoas tentando reservar o último assento disponível quase ao mesmo tempo. Se ambas consultarem o dado antes de perceber a alteração feita pela outra, as duas aplicações poderiam concluir que o assento ainda está livre. Algo semelhante pode acontecer quando uma aplicação consulta um saldo enquanto outra está processando um saque.

O **gerenciador de transações** coordena essas unidades de trabalho e sua interação. É nesse contexto que entram as propriedades **ACID**: atomicidade, consistência, isolamento e durabilidade. O conceito já havia aparecido em [[02. Modelagem de Dados/Glossário de conceitos#Propriedades ACID|Modelagem de Dados]], mas aqui ele é retomado diretamente no estudo de transações SQL e também está registrado no [[Glossário de conceitos|glossário desta disciplina]].

Neste artigo, a atomicidade aparece no princípio de tudo ou nada; o isolamento aparece na necessidade de controlar o que transações simultâneas conseguem observar umas das outras; a consistência exige que uma transação válida leve o banco de um estado válido a outro; e a durabilidade exige que alterações confirmadas sobrevivam a falhas posteriores. O log do SGBD participa especialmente dos mecanismos que tornam atomicidade e durabilidade possíveis.

## Script de prática

### SQL Server

```sql
-- testa uma inserção e desfaz
BEGIN TRANSACTION;

INSERT INTO Produto (Codigo, Nome, Preco)
VALUES (100, 'Teclado mecânico', 300);

SELECT *
FROM Produto
WHERE Codigo = 100;

ROLLBACK;


-- executa a mesma inserção e confirma
BEGIN TRANSACTION;

INSERT INTO Produto (Codigo, Nome, Preco)
VALUES (100, 'Teclado mecânico', 300);

COMMIT;


-- testa uma exclusão e desfaz
BEGIN TRANSACTION;

DELETE FROM Produto
WHERE Codigo = 100;

ROLLBACK;


-- executa a exclusão e confirma
BEGIN TRANSACTION;

DELETE FROM Produto
WHERE Codigo = 100;

COMMIT;
```

### MySQL

```sql
START TRANSACTION;

INSERT INTO Produto (Codigo, Nome, Preco)
VALUES (100, 'Teclado mecânico', 300);

ROLLBACK;


START TRANSACTION;

INSERT INTO Produto (Codigo, Nome, Preco)
VALUES (100, 'Teclado mecânico', 300);

COMMIT;
```

## Pontos que costumam gerar confusão

- **Uma transação é uma unidade lógica de trabalho, não apenas um comando SQL.** Ela pode reunir várias instruções que precisam funcionar como uma única ação.
- **Os comandos de manipulação continuam sendo os mesmos.** A novidade é agrupá-los e controlar sua confirmação ou desfazimento.
- **Mesmo sem abrir uma transação explicitamente, o SGBD pode operar em autocommit.** Nesse caso, cada instrução é confirmada individualmente.
- **`COMMIT` e `ROLLBACK` encerram a transação de maneiras diferentes.** `COMMIT` confirma; `ROLLBACK` desfaz.
- **Uma alteração pode aparecer para a própria transação antes do `COMMIT` e ainda assim ser desfeita.** A visibilidade para outras transações depende do isolamento.
- **`ROLLBACK` pode desfazer inserções, exclusões e outras alterações da transação.**
- **O log de transações não é necessariamente uma lista dos comandos SQL digitados.** Ele registra informações internas necessárias para recuperação e controle das alterações.
- **Log transacional e auditoria têm finalidades diferentes.** O primeiro sustenta recuperação e durabilidade; o segundo registra ações para rastreabilidade.
- **Atomicidade significa tudo ou nada.** Uma operação composta, como transferência bancária, não deve permanecer parcialmente concluída.
- **SQL Server e MySQL não usam exatamente a mesma sintaxe nem os mesmos mecanismos internos.** Os exemplos usam `BEGIN TRANSACTION` no SQL Server e `START TRANSACTION` no MySQL.
- **ACID é mais amplo do que atomicidade.** As quatro propriedades fazem parte deste conteúdo de transações e estão registradas no glossário de Manipulação de Dados SQL, mantendo também a conexão com Modelagem de Dados.
