# Bônus: Razor na prática no ASP.NET Core MVC

> **Contexto:** Este artigo bônus aprofunda o uso de **Razor** na camada de apresentação de aplicações ASP.NET Core MVC. O foco é entender como arquivos `.cshtml` recebem um Model do Controller, combinam HTML com C#, usam condicionais, repetições, formulários, validação, layouts e partial views e, ao final, geram HTML para o navegador. Ele complementa a definição conceitual de [[05. Desenvolvimento Web Back-End/05. Frameworks Web, MVC e mapeamento objeto-relacional#Razor|Razor no artigo 05]] e a integração entre Model, Controller e persistência do [[05. Desenvolvimento Web Back-End/06. Model, validação e persistência no ASP.NET Core MVC|artigo 06]].

Razor tende a aparecer diretamente em projetos que usam **ASP.NET Core MVC com Views renderizadas no servidor**. Se a aplicação for apenas uma API e a interface estiver em outro cliente, como React, a API pode não usar Razor para a apresentação.

O modelo mental é:

`Controller → View .cshtml + Model → Razor no servidor → HTML → navegador`

## 1. Onde Razor entra no projeto

Em ASP.NET Core MVC, uma estrutura comum é:

```text
Controllers/
└── PessoasController.cs

Models/
└── Pessoa.cs

Views/
├── Pessoas/
│   ├── Index.cshtml
│   ├── Details.cshtml
│   └── Create.cshtml
├── Shared/
│   └── _Layout.cshtml
├── _ViewImports.cshtml
└── _ViewStart.cshtml
```

O Controller escolhe uma View e pode entregar um objeto para ela:

```csharp
public IActionResult Details(int id)
{
    var pessoa = _context.Pessoas.Find(id);

    if (pessoa is null)
    {
        return NotFound();
    }

    return View(pessoa);
}
```

`View(pessoa)` envia o objeto `pessoa` para a View correspondente. O arquivo `Details.cshtml` pode então ler esse objeto por meio de `Model`.

Razor é processado **no servidor**. O navegador recebe o HTML resultante, não o código C# que estava no arquivo `.cshtml`.

## 2. O caractere `@`: transição entre HTML e C#

Um arquivo Razor continua sendo principalmente HTML:

```html
<h1>Detalhes da pessoa</h1>
<p>Conteúdo da página</p>
```

O caractere `@` indica que o Razor deve interpretar uma expressão, diretiva ou bloco de C#.

### Expressão simples

```cshtml
<p>@Model.Nome</p>
```

Se `Model.Nome` contiver `"Ana"`, o resultado enviado ao navegador será equivalente a:

```html
<p>Ana</p>
```

### Bloco de código

```cshtml
@{
    var titulo = "Detalhes";
}
```

O bloco `@{ ... }` permite executar C# durante a renderização da View.

### Expressão explícita

Quando o limite da expressão precisa ficar claro, podem ser usados parênteses:

```cshtml
<p>@(Model.Nome.ToUpper())</p>
```

### Comentário Razor

```cshtml
@* Este comentário não é enviado ao navegador. *@
```

A sintaxe comparada de templates está registrada em [[00. Sintaxe Multilinguagem/16. Templates server-side e sintaxe incorporada (Razor e PHP)|Templates server-side e sintaxe incorporada]].

## 3. `@model` e `Model`: tipo esperado versus objeto recebido

Esses dois nomes parecem quase iguais, mas cumprem papéis diferentes.

No início da View:

```cshtml
@model ExemploMvc.Models.Pessoa
```

`@model` é uma **diretiva Razor**. Ela declara qual tipo de objeto aquela View espera receber.

Depois, dentro do arquivo:

```cshtml
<h1>@Model.Nome</h1>
<p>@Model.Email</p>
```

`Model`, com M maiúsculo, é a propriedade que representa **a instância concreta recebida pela View**.

Portanto:

| Forma | Papel |
| --- | --- |
| `@model Pessoa` | Declara o tipo esperado pela View. |
| `Model` | É o objeto daquele tipo recebido durante a renderização. |
| `@Model.Nome` | Lê uma propriedade desse objeto e escreve seu valor no HTML. |

Se o Controller executa:

```csharp
return View(pessoa);
```

e a View declara:

```cshtml
@model Pessoa
```

o objeto `pessoa` passa a estar disponível dentro da View como `Model`.

## 4. Condicionais na View

Razor permite usar estruturas C# para decidir **como apresentar** determinada informação.

```cshtml
@if (Model.Ativo)
{
    <span>Usuário ativo</span>
}
else
{
    <span>Usuário inativo</span>
}
```

A condição é C#; os elementos dentro dos blocos são HTML.

Esse tipo de condição faz sentido quando a decisão é de **apresentação**. Por exemplo, mostrar ou ocultar um aviso conforme um estado já calculado.

Uma regra de negócio como “um pedido cancelado não pode ser faturado” não deveria ser implementada apenas dentro da View. Ela pertence ao domínio ou a outra camada da aplicação, como discutido em [[05. Desenvolvimento Web Back-End/05. Frameworks Web, MVC e mapeamento objeto-relacional#Model não significa apenas “classe com propriedades”|Model e regras de negócio no MVC]].

A estrutura `if/else` em C# também pode ser revisada em [[00. Sintaxe Multilinguagem/02. Estruturas condicionais (if, else, switch)|Estruturas condicionais]].

## 5. Repetindo HTML com `foreach`

Uma View que recebe uma coleção pode gerar um trecho de HTML para cada elemento.

```cshtml
@model IEnumerable<ExemploMvc.Models.Pessoa>

<ul>
@foreach (var pessoa in Model)
{
    <li>@pessoa.Nome — @pessoa.Email</li>
}
</ul>
```

Aqui:

1. `@model IEnumerable<Pessoa>` declara que a View espera uma coleção;
2. `foreach` percorre cada objeto;
3. para cada `pessoa`, o Razor produz um `<li>`;
4. o navegador recebe apenas a lista HTML já gerada.

O `foreach` é uma estrutura de repetição orientada a coleções. A referência sintática correspondente está em [[00. Sintaxe Multilinguagem/03. Estruturas de repetição (while, for, do-while)|Estruturas de repetição]].

## 6. Tag Helpers: HTML conectado ao ASP.NET Core

Razor também pode usar **Tag Helpers**, que acrescentam comportamento do ASP.NET Core a elementos que continuam parecendo HTML.

Um link pode ser escrito assim:

```cshtml
<a asp-controller="Pessoas"
   asp-action="Details"
   asp-route-id="@pessoa.Id">
    Ver detalhes
</a>
```

O Razor e os Tag Helpers transformam esses atributos em um link HTML apropriado para a rota configurada.

Outro exemplo aparece em formulários:

```cshtml
<form asp-action="Create" method="post">
    ...
</form>
```

`asp-action="Create"` relaciona o formulário à action `Create` do Controller correspondente.

Tag Helpers não são atributos HTML nativos do navegador. Eles são interpretados no servidor durante a renderização Razor e dão origem ao HTML final.

## 7. Formulários com `asp-for`

Considere:

```csharp
public class Pessoa
{
    public int Id { get; set; }

    [Required]
    public string Nome { get; set; } = string.Empty;

    [EmailAddress]
    public string Email { get; set; } = string.Empty;
}
```

Uma View de criação pode usar:

```cshtml
@model ExemploMvc.Models.Pessoa

<form asp-action="Create" method="post">
    <div>
        <label asp-for="Nome"></label>
        <input asp-for="Nome" />
        <span asp-validation-for="Nome"></span>
    </div>

    <div>
        <label asp-for="Email"></label>
        <input asp-for="Email" />
        <span asp-validation-for="Email"></span>
    </div>

    <button type="submit">Salvar</button>
</form>
```

O papel de cada Tag Helper é:

| Sintaxe | Papel |
| --- | --- |
| `asp-for="Nome"` | Associa o elemento à propriedade `Nome` do Model. |
| `asp-validation-for="Nome"` | Reserva a apresentação de mensagens de validação relacionadas à propriedade. |
| `asp-action="Create"` | Indica a action que receberá o formulário. |

Isso conecta diretamente Razor ao [[05. Desenvolvimento Web Back-End/06. Model, validação e persistência no ASP.NET Core MVC#3. Data Annotations: metadados e validação|Model e às Data Annotations]].

## 8. Como o formulário volta para o Controller

Uma action pode receber os dados enviados pelo formulário:

```csharp
[HttpPost]
public IActionResult Create(Pessoa pessoa)
{
    if (!ModelState.IsValid)
    {
        return View(pessoa);
    }

    _context.Pessoas.Add(pessoa);
    _context.SaveChanges();

    return RedirectToAction("Index");
}
```

O fluxo conceitual é:

`formulário Razor → requisição POST → model binding → Pessoa → validação → Controller`

Se o Model não for válido, o Controller pode devolver a mesma View com o objeto recebido, permitindo que os componentes de validação apresentem os erros.

A View participa da entrada e da apresentação, mas a decisão de persistir o objeto continua fora dela.

## 9. Layout: estrutura compartilhada entre páginas

Um **Layout** evita repetir a estrutura geral da página em todas as Views.

Em `Views/Shared/_Layout.cshtml`:

```cshtml
<!DOCTYPE html>
<html>
<head>
    <meta charset="utf-8" />
    <title>Minha aplicação</title>
</head>
<body>
    <header>
        <nav>Menu principal</nav>
    </header>

    <main>
        @RenderBody()
    </main>
</body>
</html>
```

`@RenderBody()` marca o ponto em que o conteúdo específico da View será inserido.

O arquivo `_ViewStart.cshtml` pode definir qual Layout será usado:

```cshtml
@{
    Layout = "_Layout";
}
```

Assim, cada View não precisa repetir `<html>`, `<head>`, navegação e outras estruturas compartilhadas.

## 10. Partial Views: reutilizar trechos de interface

Uma **Partial View** representa um fragmento de interface que pode ser reutilizado em outras Views.

Por exemplo, `_PessoaResumo.cshtml`:

```cshtml
@model ExemploMvc.Models.Pessoa

<article>
    <strong>@Model.Nome</strong>
    <span>@Model.Email</span>
</article>
```

Outra View pode reutilizá-la:

```cshtml
@foreach (var pessoa in Model)
{
    <partial name="_PessoaResumo" model="pessoa" />
}
```

O objetivo é evitar duplicação de marcação e organizar melhor a apresentação.

Uma Partial View continua pertencendo à camada de apresentação. Ela não é um substituto para Model, serviço ou Controller.

## 11. Exemplo completo de uma View de detalhes

```cshtml
@model ExemploMvc.Models.Pessoa

<h1>Detalhes</h1>

@if (Model is null)
{
    <p>Pessoa não encontrada.</p>
}
else
{
    <dl>
        <dt>Nome</dt>
        <dd>@Model.Nome</dd>

        <dt>E-mail</dt>
        <dd>@Model.Email</dd>
    </dl>

    <a asp-action="Index">Voltar</a>
}
```

Nesse arquivo aparecem juntas as ideias principais:

- `@model` declara o tipo;
- `Model` representa o objeto recebido;
- `@if` controla apresentação;
- `@Model.Nome` escreve dados no HTML;
- `asp-action` usa um Tag Helper para gerar navegação.

## 12. O que deve e o que não deve ficar em Razor

Razor pode executar C#, mas isso não significa que qualquer lógica deva ser colocada na View.

| Faz sentido na View | É melhor ficar fora da View |
| --- | --- |
| Escolher como apresentar um valor | Consultar diretamente o banco |
| Mostrar ou ocultar trechos de interface | Aplicar regra central de negócio |
| Percorrer uma coleção para gerar HTML | Alterar entidades persistentes |
| Formatar informações para apresentação | Chamar `SaveChanges()` |
| Reutilizar layout e partials | Coordenar vários serviços do domínio |

Um sinal de alerta é encontrar algo como:

```cshtml
@{
    var pessoas = _context.Pessoas.ToList();
}
```

A View não deveria assumir o papel de acesso ao banco. O Controller ou uma camada apropriada deve preparar os dados e entregá-los à View.

A divisão permanece:

`Controller coordena → Model/serviços aplicam comportamento → View Razor apresenta`

## 13. Razor, Razor Pages e Blazor não são a mesma coisa

**Razor** é a sintaxe de marcação que combina HTML e C#.

Essa sintaxe aparece em diferentes modelos:

- **ASP.NET Core MVC:** Razor é usado principalmente nas Views `.cshtml`;
- **Razor Pages:** organiza a aplicação em páginas com seus próprios handlers;
- **Blazor:** usa sintaxe Razor para construir componentes, mas possui um modelo de componentes e execução diferente do MVC tradicional.

Portanto, aprender a sintaxe Razor ajuda em mais de uma tecnologia .NET, mas este artigo está focado no seu uso em **Views do ASP.NET Core MVC**.

## 14. Checklist mental para os projetos

Ao encontrar uma View `.cshtml`, procure responder:

1. Qual tipo está declarado em `@model`?
2. Qual objeto o Controller enviou para essa View?
3. Onde `Model` é lido?
4. Há condicionais ou repetições apenas para apresentação?
5. O formulário usa `asp-for`, `asp-action` ou validação?
6. A View está usando um Layout ou Partial?
7. Alguma regra de negócio ou acesso ao banco foi indevidamente colocado dentro da View?

Se essas respostas estiverem claras, o papel de Razor no fluxo MVC também tende a estar claro.
