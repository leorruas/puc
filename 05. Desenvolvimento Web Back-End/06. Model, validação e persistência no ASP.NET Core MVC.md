# Model, validação e persistência no ASP.NET Core MVC

> **Contexto:** Este artigo aprofunda o papel do Model no ASP.NET Core MVC e conecta Data Annotations, Entity Framework Core, `ApplicationDbContext`, injeção de dependência, connection string, migrations e consulta de entidades em um único fluxo. Também distingue o padrão antigo com `Startup.cs` da configuração atual concentrada em `Program.cs`.

O [[05. Desenvolvimento Web Back-End/05. Frameworks Web, MVC e mapeamento objeto-relacional|artigo 05]] apresentou MVC e ORM separadamente. Aqui essas peças passam a funcionar juntas. O ponto central é entender o caminho que liga uma classe C# ao banco de dados e, depois, ao controller: o **Model representa os dados**, o **EF Core faz o mapeamento**, o **DbContext coordena o acesso ao banco** e a **injeção de dependência entrega esse contexto ao controller**.

## O mapa mental antes do código

Antes de olhar a sintaxe, vale separar as responsabilidades:

| Peça | Função no fluxo |
| --- | --- |
| `Pessoa` | Classe que representa os dados manipulados pela aplicação. |
| Data Annotations | Metadados colocados nas propriedades para indicar validação, exibição e aspectos do mapeamento. |
| `ApplicationDbContext` | Contexto do EF Core que conhece as entidades e coordena consultas e persistência. |
| `DbSet<Pessoa>` | Ponto de acesso às entidades `Pessoa` dentro do contexto. |
| Connection string | Informa ao provedor como localizar e acessar o banco. |
| Migration | Registra alterações no modelo que precisam ser refletidas no esquema do banco. |
| Controller | Recebe o `ApplicationDbContext` por injeção de dependência e o utiliza para consultar ou alterar dados. |

Em uma leitura de ponta a ponta, o fluxo é este: a aplicação define `Pessoa`; o contexto inclui `Pessoa` no modelo persistente; a configuração registra o contexto e o banco; migrations criam ou atualizam o esquema; e o controller usa o contexto para buscar ou modificar entidades.

## O que significa Model no MVC?

No MVC, **Model** é a parte relacionada aos dados, ao estado e às regras que a aplicação manipula. No exemplo estudado, uma classe simples representa uma pessoa:

```csharp
public class Pessoa
{
    public int Id { get; set; }
    public string Nome { get; set; } = string.Empty;
    public string Email { get; set; } = string.Empty;
}
```

Essa classe não é, por definição, uma tabela. Ela é primeiro um **tipo C#**. Quando o Entity Framework Core passa a mapear `Pessoa`, suas propriedades podem ser associadas a colunas de uma estrutura relacional.

Também é importante não transformar “Model” em sinônimo de “entidade do banco”. Em aplicações maiores, podem existir entidades persistentes, modelos de domínio, DTOs e view models diferentes. Neste exemplo introdutório, a mesma classe `Pessoa` ocupa um papel simples o suficiente para aproximar essas ideias.

Um **DTO (Data Transfer Object)** é um objeto criado principalmente para **transportar dados entre partes do sistema**, sem precisar representar diretamente a entidade persistida no banco. Ele costuma conter apenas os campos necessários para uma operação específica.

Por exemplo, a entidade `Pessoa` poderia ter várias propriedades internas, enquanto um DTO usado para cadastrar uma pessoa poderia carregar somente:

```csharp
public class CriarPessoaDto
{
    public string Nome { get; set; } = string.Empty;
    public string Email { get; set; } = string.Empty;
}
```

A ideia é separar **como os dados são armazenados internamente** de **quais dados entram ou saem em determinada operação**. Um DTO não é uma tabela e não precisa ser mapeado pelo EF Core.

## Data Annotations: metadados diretamente no Model

**Data Annotations** são atributos colocados sobre classes ou propriedades para fornecer metadados ao .NET e aos frameworks que interpretam esses atributos.

Um modelo reorganizado pode ficar assim:

```csharp
using System.ComponentModel.DataAnnotations;

public class Pessoa
{
    [Key]
    public int Id { get; set; }

    [Display(Name = "Nome")]
    [Required(ErrorMessage = "Obrigatório informar o nome.")]
    [MaxLength(100, ErrorMessage = "Máximo de 100 caracteres.")]
    public string Nome { get; set; } = string.Empty;

    [Display(Name = "E-mail")]
    [Required(ErrorMessage = "Obrigatório informar o e-mail.")]
    [EmailAddress(ErrorMessage = "Informe um e-mail válido.")]
    public string Email { get; set; } = string.Empty;
}
```

Cada atributo tem uma responsabilidade diferente:

| Atributo | Papel |
| --- | --- |
| `[Key]` | Marca a propriedade que identifica a entidade quando a convenção não for suficiente ou quando se quiser tornar essa intenção explícita. |
| `[Display]` | Define metadados de apresentação, como o nome exibido para o campo. |
| `[Required]` | Define que um valor é obrigatório para a validação do modelo. |
| `[MaxLength]` | Limita o comprimento aceito e também pode influenciar o mapeamento relacional do EF Core. |
| `[EmailAddress]` | Valida se o valor possui formato de endereço de e-mail. |

### `DataType.EmailAddress` não é a mesma coisa que validar e-mail

`[DataType(DataType.EmailAddress)]` informa o **tipo semântico de dado** para fins de apresentação e geração de interface, mas `DataType` não realiza a validação do formato por si só. Para validar um endereço de e-mail, a forma apropriada é `[EmailAddress]`.

A distinção é útil porque duas coisas diferentes estão acontecendo: **metadados de apresentação** dizem como tratar ou exibir um campo; **atributos de validação** verificam se o valor recebido atende a uma regra.

## O que significa “contexto” no EF Core?

Aqui, **contexto não é o banco de dados**. O banco é o lugar onde os dados ficam persistidos. O **contexto** é um objeto da aplicação que representa a interface de trabalho do Entity Framework Core com esse banco durante uma unidade de trabalho.

Uma forma simples de pensar é: o banco é o **arquivo onde os dados moram**; o `DbContext` é a **mesa de trabalho** usada pela aplicação para abrir, consultar, acompanhar alterações e mandar salvar esses dados.

O contexto conhece o modelo de entidades da aplicação, disponibiliza conjuntos como `DbSet<Pessoa>`, coordena consultas, acompanha objetos carregados ou modificados e envia as mudanças ao banco quando `SaveChanges()` ou `SaveChangesAsync()` é chamado.

Por isso, é importante separar estas peças:

| Peça | O que é |
| --- | --- |
| Banco de dados | Armazenamento persistente real, com tabelas, linhas, chaves e outras estruturas. |
| `DbContext` | Objeto C# do EF Core que coordena o trabalho da aplicação com o banco. |
| `ApplicationDbContext` | Classe específica da aplicação que herda de `DbContext` e define quais entidades fazem parte daquele modelo. |
| `DbSet<Pessoa>` | Ponto de acesso do contexto às entidades `Pessoa`. |
| Connection string | Configuração que informa onde está o banco e como acessá-lo. |
| Provider | Componente do EF Core que traduz as operações para o banco específico, como SQL Server ou SQLite. |

Assim, quando aparece:

```csharp
private readonly ApplicationDbContext _context;
```

`_context` **não contém o banco inteiro dentro dele**. Ele é apenas a referência ao objeto que o controller usa para conversar com o EF Core e, por meio dele, com o banco.

## `ApplicationDbContext`: a ponte entre o modelo C# e o banco

O `DbContext` é a classe central do EF Core. Uma aplicação normalmente cria uma classe própria que herda dele e declara quais entidades fazem parte daquele modelo persistente.

Uma versão simples seria:

```csharp
using Microsoft.EntityFrameworkCore;

public class ApplicationDbContext : DbContext
{
    public ApplicationDbContext(
        DbContextOptions<ApplicationDbContext> options)
        : base(options)
    {
    }

    public DbSet<Pessoa> Pessoas => Set<Pessoa>();
}
```

O construtor recebe `DbContextOptions<ApplicationDbContext>`. Esse objeto contém a configuração necessária para aquele contexto, como o provedor de banco utilizado e sua connection string. O `: base(options)` repassa a configuração para a classe `DbContext`.

Já `DbSet<Pessoa>` fornece o ponto de entrada para consultar e persistir entidades `Pessoa`. É uma abstração do modelo do EF Core; não deve ser entendido literalmente como “a tabela em memória”.

## Por que aparece `IdentityDbContext<ApplicationUser>`?

Um dos exemplos estudados declara o contexto desta forma:

```csharp
public class ApplicationDbContext
    : IdentityDbContext<ApplicationUser>
{
    // ...
}
```

Isso significa que a aplicação está combinando EF Core com **ASP.NET Core Identity**, infraestrutura usada para contas de usuário, autenticação, papéis e outros dados de identidade. `IdentityDbContext` já inclui o modelo necessário para entidades do Identity e continua funcionando como um `DbContext`.

Por isso, quando a migration é aplicada, aparecem tabelas como `AspNetUsers`, `AspNetRoles`, `AspNetUserClaims` e outras, além da tabela `Pessoas`. Essas tabelas adicionais não foram criadas por `DbSet<Pessoa>`; elas vêm do modelo de Identity incorporado ao contexto.

Se a aplicação não utilizar ASP.NET Core Identity, o contexto pode herdar diretamente de `DbContext`. Portanto, `IdentityDbContext` não é um requisito geral para usar EF Core.

## Injeção de dependência: como o controller recebe o contexto

O ASP.NET Core possui um contêiner de **injeção de dependência (DI)**. Em vez de o controller criar manualmente um `ApplicationDbContext` com `new`, ele declara que precisa dessa dependência no construtor.

```csharp
public class PessoasController : Controller
{
    private readonly ApplicationDbContext _context;

    public PessoasController(ApplicationDbContext context)
    {
        _context = context;
    }
}
```

A leitura linha por linha ajuda:

- `private readonly ApplicationDbContext _context;` cria um campo privado que guardará a dependência;
- `readonly` indica que a referência deve ser definida na inicialização do objeto e não ficar sendo trocada depois;
- o construtor solicita um `ApplicationDbContext`;
- o ASP.NET Core encontra uma instância registrada desse tipo no contêiner de serviços;
- a instância recebida é armazenada em `_context`.

Isso é **injeção por construtor**. O controller declara sua necessidade; a infraestrutura resolve e fornece a dependência.

A principal diferença mental é esta:

```csharp
// Acoplamento direto: a própria classe tenta construir sua dependência.
var contexto = new ApplicationDbContext(...);

// Injeção de dependência: a classe apenas declara o que precisa.
public PessoasController(ApplicationDbContext context)
```

Esse mecanismo reduz o acoplamento da criação das dependências com a lógica do controller e facilita configuração, manutenção e testes.

## Registrando o `DbContext` na aplicação

Para que o ASP.NET Core consiga injetar `ApplicationDbContext`, esse tipo precisa ser registrado no contêiner de serviços.

Em versões anteriores do ASP.NET Core, essa configuração aparecia em `Startup.cs` e `ConfigureServices`:

```csharp
public void ConfigureServices(IServiceCollection services)
{
    services.AddDbContext<ApplicationDbContext>(options =>
        options.UseSqlServer(
            Configuration.GetConnectionString("DefaultConnection")));
}
```

A ideia continua atual: `AddDbContext<ApplicationDbContext>` registra o contexto e `UseSqlServer(...)` configura o provedor SQL Server.

Em projetos ASP.NET Core atuais, essa configuração costuma aparecer em `Program.cs`:

```csharp
var connectionString =
    builder.Configuration.GetConnectionString("DefaultConnection")
    ?? throw new InvalidOperationException(
        "Connection string 'DefaultConnection' não encontrada.");

builder.Services.AddDbContext<ApplicationDbContext>(options =>
    options.UseSqlServer(connectionString));
```

Assim, quando o framework precisar criar `PessoasController`, ele consegue resolver o parâmetro `ApplicationDbContext context` do construtor.

### E as chamadas de Identity?

Trechos como estes:

```csharp
.AddEntityFrameworkStores<ApplicationDbContext>()
.AddDefaultTokenProviders();
```

pertencem à configuração do **ASP.NET Core Identity**. Eles não são necessários apenas para usar EF Core com a entidade `Pessoa`. Essa separação evita misturar dois assuntos: uma coisa é persistência com EF Core; outra é a infraestrutura de identidade que também usa EF Core para armazenar usuários e papéis.

## Connection string e `appsettings.json`

A **connection string** reúne informações usadas pelo provedor para localizar e acessar o banco. No ASP.NET Core, ela pode ser registrada em `appsettings.json`:

```json
{
  "ConnectionStrings": {
    "DefaultConnection": "Server=SEU_SERVIDOR;Database=SeuBanco;Trusted_Connection=True;"
  }
}
```

O nome `DefaultConnection` não possui comportamento mágico. É apenas a chave escolhida para recuperar aquela configuração:

```csharp
builder.Configuration.GetConnectionString("DefaultConnection")
```

Um exemplo com SQL Server LocalDB utiliza:

```text
Server=(localdb)\\mssqllocaldb;...
```

Esse endereço aponta para **SQL Server LocalDB**, tecnologia específica do Windows. No macOS, essa connection string não funciona. A lógica de `DbContext`, injeção de dependência, `DbSet` e migrations continua a mesma, mas o provedor e a connection string precisam corresponder ao banco realmente utilizado. O [[05. Desenvolvimento Web Back-End/05. Frameworks Web, MVC e mapeamento objeto-relacional#Usando EF Core no macOS|artigo 05]] já registra as alternativas para macOS.

## Migrations: transformando o modelo em esquema

Depois que o modelo e o contexto existem, o EF Core pode gerar uma **migration** para representar as mudanças necessárias no esquema.

No Package Manager Console do Visual Studio:

```powershell
Add-Migration Initial
Update-Database
```

Na CLI do .NET:

```bash
dotnet ef migrations add Initial
dotnet ef database update
```

Os comandos têm papéis diferentes:

1. `Add-Migration` ou `dotnet ef migrations add` gera arquivos que descrevem a alteração do esquema;
2. `Update-Database` ou `dotnet ef database update` aplica as migrations pendentes ao banco.

Quando o contexto inclui `Pessoa` e também herda de `IdentityDbContext`, a migration precisa representar **todo o modelo conhecido pelo contexto**. É por isso que o banco pode ganhar a tabela `Pessoas` e várias tabelas `AspNet...` na mesma estrutura.

Também aparece uma tabela chamada `__EFMigrationsHistory`. Ela é usada pelo EF Core para registrar quais migrations já foram aplicadas àquele banco.

## Consultando uma entidade no controller

Depois que o contexto foi injetado, o controller pode usar `DbSet<Pessoa>` para consultar dados.

Uma consulta básica por chave primária é:

```csharp
Pessoa? pessoa = _context.Pessoas.Find(id);
```

A leitura é simples:

- `_context` é o contexto recebido pelo construtor;
- `Pessoas` é o `DbSet<Pessoa>`;
- `Find(id)` procura uma entidade pela chave primária;
- o resultado pode ser uma `Pessoa` ou `null`.

Em uma action MVC:

```csharp
public IActionResult Details(int id)
{
    var pessoa = _context.Pessoas.Find(id);

    if (pessoa is null)
    {
        return NotFound();
    }

    return View(pessoa);
}
```

Em código atual também é comum usar a versão assíncrona:

```csharp
public async Task<IActionResult> Details(int id)
{
    var pessoa = await _context.Pessoas.FindAsync(id);

    if (pessoa is null)
    {
        return NotFound();
    }

    return View(pessoa);
}
```

`Find` e `FindAsync` são adequados quando a busca é pela chave primária. Para procurar por outros campos ou montar consultas mais complexas, entram consultas LINQ.

## Fluxo completo: da classe até a resposta MVC

Agora as peças podem ser lidas como uma sequência única:

1. **`Pessoa` define o formato dos dados no código.**
2. **Data Annotations acrescentam metadados e regras de validação.**
3. **`ApplicationDbContext` inclui `Pessoa` no modelo do EF Core por meio de `DbSet<Pessoa>`.**
4. **`AddDbContext` registra o contexto e configura o provedor e a connection string.**
5. **Migrations transformam mudanças do modelo em alterações de esquema no banco.**
6. **O ASP.NET Core cria o controller e injeta um `ApplicationDbContext` pelo construtor.**
7. **O controller usa `_context.Pessoas` para consultar ou persistir entidades e envia os dados necessários para a View.**

A ideia de injeção de dependência fecha uma lacuna importante do [[05. Desenvolvimento Web Back-End/05. Frameworks Web, MVC e mapeamento objeto-relacional|artigo 05]]: antes sabíamos o que era um `DbContext`; agora sabemos **como ele chega ao controller sem o controller precisar construí-lo**.

## Exemplo integrado

A seguir, as peças aparecem juntas em uma versão atual e enxuta.

### `Pessoa.cs`

```csharp
using System.ComponentModel.DataAnnotations;

namespace ExemploMvc.Models;

public class Pessoa
{
    [Key]
    public int Id { get; set; }

    [Display(Name = "Nome")]
    [Required(ErrorMessage = "Obrigatório informar o nome.")]
    [MaxLength(100)]
    public string Nome { get; set; } = string.Empty;

    [Display(Name = "E-mail")]
    [Required(ErrorMessage = "Obrigatório informar o e-mail.")]
    [EmailAddress(ErrorMessage = "Informe um e-mail válido.")]
    public string Email { get; set; } = string.Empty;
}
```

### `ApplicationDbContext.cs`

```csharp
using ExemploMvc.Models;
using Microsoft.EntityFrameworkCore;

namespace ExemploMvc.Data;

public class ApplicationDbContext : DbContext
{
    public ApplicationDbContext(
        DbContextOptions<ApplicationDbContext> options)
        : base(options)
    {
    }

    public DbSet<Pessoa> Pessoas => Set<Pessoa>();
}
```

### `Program.cs`

```csharp
using ExemploMvc.Data;
using Microsoft.EntityFrameworkCore;

var builder = WebApplication.CreateBuilder(args);

var connectionString =
    builder.Configuration.GetConnectionString("DefaultConnection")
    ?? throw new InvalidOperationException(
        "Connection string 'DefaultConnection' não encontrada.");

builder.Services.AddControllersWithViews();

builder.Services.AddDbContext<ApplicationDbContext>(options =>
    options.UseSqlServer(connectionString));

var app = builder.Build();

app.UseHttpsRedirection();
app.UseStaticFiles();
app.UseRouting();

app.MapControllerRoute(
    name: "default",
    pattern: "{controller=Home}/{action=Index}/{id?}");

app.Run();
```

Em projetos ASP.NET Core modernos, o código acima utiliza **top-level statements**; o compilador gera o ponto de entrada equivalente ao `Main` tradicional.

### `PessoasController.cs`

```csharp
using ExemploMvc.Data;
using Microsoft.AspNetCore.Mvc;

namespace ExemploMvc.Controllers;

public class PessoasController : Controller
{
    private readonly ApplicationDbContext _context;

    public PessoasController(ApplicationDbContext context)
    {
        _context = context;
    }

    public async Task<IActionResult> Details(int id)
    {
        var pessoa = await _context.Pessoas.FindAsync(id);

        if (pessoa is null)
        {
            return NotFound();
        }

        return View(pessoa);
    }
}
```

### `appsettings.json`

```json
{
  "ConnectionStrings": {
    "DefaultConnection": "Server=SEU_SERVIDOR;Database=SeuBanco;Trusted_Connection=True;"
  }
}
```

Com esses arquivos, o encadeamento conceitual fica visível no próprio código: configuração → registro no contêiner → injeção no controller → consulta pelo `DbSet`.

## O que mudou em relação ao padrão antigo?

| Padrão antigo | Em projetos atuais | O conceito permanece? |
| --- | --- | --- |
| Configuração em `Startup.ConfigureServices` | Configuração normalmente concentrada em `Program.cs` | Sim: serviços continuam registrados no contêiner de DI. |
| `[DataType(DataType.EmailAddress)]` usado como se validasse formato | `[EmailAddress]` para validação de e-mail | Sim: Data Annotations continuam sendo usadas, mas os atributos têm papéis diferentes. |
| SQL Server LocalDB | Continua disponível no Windows; outros ambientes usam outro servidor/provedor | Sim: o `DbContext` continua precisando de provedor e configuração. |
| `Find(id)` | `Find(id)` continua válido; `FindAsync(id)` é comum em código assíncrono | Sim. |
| `IdentityDbContext<ApplicationUser>` | Continua existindo quando ASP.NET Core Identity faz parte da aplicação | Não é obrigatório para aplicações que usam apenas EF Core. |

O objetivo não é decorar duas versões do framework. É reconhecer a estrutura que permanece estável mesmo quando a sintaxe de inicialização muda: **registrar serviços, configurar o contexto, injetar dependências e operar sobre entidades**.

## Pontos que costumam gerar confusão

- **Model não é sinônimo de tabela.** A classe é um objeto C#; o ORM pode mapeá-la para uma estrutura relacional.
- **`DbContext` não é o banco de dados.** É o objeto da aplicação que coordena o acesso do EF Core ao banco, incluindo consultas, rastreamento de entidades e persistência.
- **`DbSet<Pessoa>` não é literalmente a tabela `Pessoas`.** É a abstração do EF Core para trabalhar com aquele conjunto de entidades.
- **Data Annotation não significa automaticamente validação.** `[Display]` e `[DataType]` fornecem metadados; `[Required]`, `[MaxLength]` e `[EmailAddress]` podem impor regras de validação.
- **Injeção de dependência não cria um novo contexto manualmente dentro do controller.** O controller declara a dependência e o ASP.NET Core a fornece.
- **`private readonly ApplicationDbContext _context` é o campo; `ApplicationDbContext context` é o parâmetro recebido pelo construtor.**
- **`AddDbContext` registra e configura o contexto; não executa uma consulta ao banco.**
- **Connection string e `DbContext` são coisas diferentes.** A connection string descreve como acessar o banco; o contexto coordena o trabalho do EF Core.
- **Migration não é consulta de dados.** Ela representa evolução do esquema do banco.
- **As tabelas `AspNet...` vêm do ASP.NET Core Identity.** Elas não são geradas simplesmente porque existe uma entidade `Pessoa`.
- **`DefaultConnection` é apenas um nome de configuração.** Pode ser substituído por outro nome se o código usar a mesma chave.
- **A connection string com `(localdb)\\mssqllocaldb` é específica do Windows.** No macOS é necessário outro ambiente de banco.
- **`Startup.cs` não precisa ser decorado como a única forma de configurar ASP.NET Core.** O padrão atual concentra normalmente essa inicialização em `Program.cs`.
