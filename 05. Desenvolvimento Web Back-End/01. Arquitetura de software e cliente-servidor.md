# Arquitetura de software e cliente-servidor

Arquitetura de software trata das decisões estruturais mais importantes de um sistema: quais partes existem, como elas se relacionam, quais responsabilidades assumem, como o sistema se encaixa em seu ambiente e quais princípios orientam sua evolução. Ela não é apenas um desenho técnico nem uma lista de tecnologias. É uma forma de organizar decisões que terão impacto sobre desempenho, segurança, manutenção, escalabilidade e outras qualidades do sistema.

A arquitetura cliente-servidor é especialmente importante para desenvolvimento Web Back-End. Nesse contexto, o navegador ou outro cliente envia requisições, enquanto o servidor recebe essas requisições, executa processamento e devolve respostas.

## O que é arquitetura de software

A ISO/IEC/IEEE 42010 trata arquitetura como os conceitos ou propriedades fundamentais de uma entidade em seu ambiente e os princípios que orientam sua realização e evolução. A edição atual da norma é a ISO/IEC/IEEE 42010:2022. Formulações de versões anteriores explicitavam elementos, relacionamentos e princípios de design e evolução.

A ideia central permanece a mesma: a arquitetura não descreve apenas quais componentes existem, mas também como eles se relacionam e quais decisões estruturais permitem que o sistema cumpra seus objetivos.

Bass, Clements e Kazman apresentam uma definição clássica de arquitetura de software baseada nas estruturas do sistema, nos elementos de software, nas propriedades externamente visíveis desses elementos e nas relações entre eles. Essa definição ajuda a perceber que arquitetura trabalha principalmente com aquilo que é relevante para compreender o sistema como um conjunto, e não com cada detalhe interno de implementação.

## Arquitetura não é a mesma coisa que descrição da arquitetura

É útil separar a **arquitetura** do sistema de sua **descrição arquitetural**.

A arquitetura é a organização e o conjunto de decisões que existem no sistema. A descrição arquitetural é o artefato usado para comunicar essa arquitetura: diagramas, documentos, modelos, decisões registradas e outras representações.

Uma mesma arquitetura pode ser apresentada por diferentes **visões**, dependendo da preocupação de quem está observando. Um desenvolvedor pode precisar enxergar módulos e dependências; uma equipe de infraestrutura pode precisar enxergar servidores, processos e implantação; uma equipe de segurança pode precisar enxergar fluxos de dados, fronteiras de confiança e mecanismos de autenticação.

Por isso, um diagrama isolado não é "a arquitetura inteira". Ele representa uma visão dela.

## O que pode fazer parte de uma arquitetura

Uma dúvida importante é se arquitetura significa hardware, sistema centralizado ou distribuído, Web, mobile ou framework.

Essas coisas não estão no mesmo nível.

Uma arquitetura pode envolver decisões sobre **estrutura do software**, **distribuição dos componentes**, **comunicação**, **persistência de dados**, **implantação**, **infraestrutura** e **integração com sistemas externos**. Portanto, hardware ou infraestrutura podem fazer parte de uma visão arquitetural, especialmente quando afetam o funcionamento do sistema.

Já termos como **centralizado** e **distribuído** descrevem formas possíveis de organização. **Web** e **mobile** indicam principalmente contextos ou plataformas de aplicação. Um **framework**, como ASP.NET, Express, Django ou Spring, é uma tecnologia usada para implementar partes da solução. Escolher um framework pode influenciar a arquitetura, mas framework e arquitetura não são sinônimos.

Uma forma simples de pensar é:

> arquitetura responde principalmente a "como o sistema está organizado e quais decisões estruturais governam seu funcionamento"; tecnologias e frameworks respondem a "com quais ferramentas vamos implementar essas decisões".

## Cliente e servidor

No desenvolvimento Web, uma organização muito comum é a arquitetura **cliente-servidor**.

O **cliente** inicia uma comunicação. Em uma aplicação Web, esse papel costuma ser exercido pelo navegador. O cliente envia uma requisição HTTP solicitando algum recurso ou operação.

O **servidor** recebe a requisição, decide como tratá-la e devolve uma resposta HTTP. Dependendo do caso, ele pode simplesmente localizar um arquivo, executar código da aplicação, consultar um banco de dados, verificar permissões, transformar dados ou conversar com outros serviços antes de produzir a resposta.

Um fluxo simplificado pode ser representado assim:

```text
cliente → requisição HTTP → servidor
cliente ← resposta HTTP   ← servidor
```

Em uma aplicação dinâmica, normalmente existe mais coisa por trás do "servidor":

```text
navegador
   ↓ HTTP
servidor Web / aplicação
   ↓
regras da aplicação
   ↓
banco de dados ou outros serviços
```

Essa separação pode ser **lógica**, mesmo quando tudo é executado na mesma máquina, ou **física**, quando diferentes componentes ficam em máquinas, contêineres ou serviços distintos.

## Client-side e server-side

**Client-side** é aquilo que executa no lado do cliente. No caso da Web, normalmente estamos falando do navegador. HTML estrutura o documento, CSS define sua apresentação e JavaScript executa comportamento no navegador.

**Server-side** é aquilo que executa no servidor. O código pode ser escrito em linguagens e plataformas diferentes, como JavaScript com Node.js, C# com ASP.NET, Java com Spring, Python com Django ou outras opções.

O código server-side pode autenticar usuários, aplicar regras de negócio, consultar bancos de dados, gerar conteúdo, processar arquivos, enviar mensagens e executar operações que não deveriam depender do navegador do usuário.

## O servidor sempre devolve HTML, CSS e JavaScript?

Não. Essa afirmação, se tomada literalmente, está errada.

Uma resposta HTTP pode carregar muitos tipos diferentes de conteúdo. O servidor pode responder com:

- HTML;
- JSON;
- XML;
- CSS;
- JavaScript;
- imagens;
- vídeos;
- PDFs;
- arquivos para download;
- texto simples;
- ou até uma resposta sem corpo.

O cabeçalho HTTP `Content-Type` informa ao cliente qual é o tipo do conteúdo devolvido. Exemplos incluem `text/html`, `application/json`, `text/css` e `image/png`.

Quando o navegador recebe uma página HTML, esse HTML pode conter referências a outros recursos. Nesse caso, o navegador normalmente envia **novas requisições HTTP** para buscar CSS, JavaScript, imagens, fontes e outros arquivos.

Portanto, não existe necessariamente uma única resposta contendo "HTML + CSS + JavaScript". Um carregamento de página costuma envolver várias requisições e várias respostas.

Um exemplo simplificado:

```text
GET /pagina
→ resposta: text/html

GET /style.css
→ resposta: text/css

GET /app.js
→ resposta: application/javascript

GET /logo.png
→ resposta: image/png
```

Além disso, aplicações modernas frequentemente fazem requisições para APIs. Nesse caso, o servidor pode devolver apenas dados:

```text
GET /api/usuarios/42
→ resposta: application/json
```

```json
{
  "id": 42,
  "nome": "Ana"
}
```

O JavaScript executado no navegador recebe esses dados e atualiza a interface. Um aplicativo mobile também pode consumir a mesma API sem utilizar HTML, CSS ou JavaScript provenientes daquele servidor.

## Conteúdo estático e conteúdo dinâmico

Um servidor pode entregar **conteúdo estático**, como um arquivo que já existe no sistema de arquivos. Uma requisição para uma imagem ou uma folha de estilos pode simplesmente resultar na leitura e no envio daquele arquivo.

Em outros casos, a resposta é **gerada dinamicamente**. A aplicação recebe informações da requisição, executa alguma lógica e produz uma resposta específica.

Por exemplo:

```text
GET /produtos/25
      ↓
aplicação identifica o produto 25
      ↓
consulta o banco de dados
      ↓
obtém os dados do produto
      ↓
gera HTML ou JSON
      ↓
envia a resposta
```

A diferença principal está em a resposta já existir pronta ou precisar ser produzida a partir do estado e das regras da aplicação.

## Estilos arquiteturais

Um **estilo arquitetural** define uma forma recorrente de organizar partes de um sistema e impõe certas relações ou restrições entre elas. Cliente-servidor é um exemplo.

Outros estilos podem enfatizar separação em camadas, eventos, serviços distribuídos ou outras formas de organização. O ponto importante é que estilos fornecem soluções estruturais já conhecidas para tipos recorrentes de problema.

Um sistema não precisa ser descrito por um único estilo puro. Sua arquitetura pode combinar diferentes ideias arquiteturais. Por exemplo, uma aplicação pode usar cliente-servidor na comunicação externa e organização em camadas dentro do servidor.

Também é importante não tratar **estilo arquitetural**, **padrão arquitetural** e **design pattern** como se fossem exatamente a mesma coisa. Os termos são próximos e a literatura nem sempre estabelece fronteiras idênticas, mas padrões de projeto, como os estudados em [[01. Programacao Modular/24. Padrões de projeto (design patterns) e o catálogo GoF|Programação Modular]], normalmente atuam em uma escala menor que decisões arquiteturais do sistema inteiro.

## Características arquiteturais

Além das funções que o sistema precisa oferecer, existem propriedades relacionadas a **como ele deve funcionar**. Elas aparecem com vários nomes na literatura: características arquiteturais, atributos de qualidade e requisitos não funcionais.

Não existe uma taxonomia única e universal. A divisão entre características **operacionais**, **estruturais** e **transversais** é uma forma possível de organizá-las, e não uma classificação obrigatória para todos os projetos.

### Características operacionais

As características operacionais estão ligadas ao comportamento do sistema durante sua execução.

**Desempenho** envolve medidas como tempo de resposta, latência, vazão (*throughput*) e uso de recursos. Portanto, é mais amplo do que apenas medir a resposta de um sistema sem carga.

**Escalabilidade** é a capacidade de continuar atendendo adequadamente quando a carga aumenta, por exemplo, com crescimento do número de usuários, requisições ou volume de dados.

**Elasticidade** é a capacidade de aumentar ou diminuir recursos de acordo com a demanda. Um sistema pode ser escalável sem ser automaticamente elástico.

**Disponibilidade** indica quanto tempo ou em que proporção o sistema precisa permanecer acessível e operacional.

**Confiabilidade** está relacionada à capacidade de executar corretamente suas funções durante determinado período e sob determinadas condições. Sistemas críticos podem exigir níveis muito altos de confiabilidade.

**Continuidade** está associada à possibilidade de manter ou restabelecer serviços diante de incidentes e desastres.

**Recuperabilidade** trata da capacidade e da velocidade de recuperar o funcionamento e os dados depois de uma falha.

**Robustez** indica a capacidade de lidar adequadamente com entradas inesperadas, erros, situações de limite e falhas sem entrar em estados inadequados.

### Características estruturais

As características estruturais dizem respeito principalmente à organização interna e à facilidade de evolução do sistema.

**Modularidade** busca dividir o sistema em partes com responsabilidades bem definidas.

**Acoplamento** descreve o grau de dependência entre partes do sistema. Em geral, reduzir dependências desnecessárias facilita mudanças e testes. Esse conceito já foi estudado em [[01. Programacao Modular/04. Programação orientada a objetos e acoplamento|Programação Modular]].

**Legibilidade** está mais diretamente associada ao código e à facilidade de compreensão da implementação, mas pode contribuir para manutenibilidade.

**Instalabilidade** envolve a facilidade de instalar e preparar o sistema nos ambientes necessários.

**Localização** envolve adaptar o software para idiomas, formatos de data, moedas, unidades de medida e convenções locais.

**Extensibilidade** é a facilidade de adicionar novas funcionalidades sem provocar mudanças excessivas no restante do sistema.

**Configurabilidade** indica até que ponto comportamentos podem ser modificados por configuração em vez de exigir alterações no código.

**Portabilidade** representa a capacidade de executar ou ser adaptado para diferentes ambientes e plataformas.

**Manutenibilidade** é a facilidade de corrigir, modificar e aprimorar o sistema ao longo do tempo.

**Suportabilidade** está relacionada à facilidade de diagnosticar, operar e prestar suporte ao sistema.

**Atualizabilidade** envolve a facilidade e a segurança com que novas versões podem ser implantadas.

### Características transversais

Algumas características atravessam diferentes partes da arquitetura e não ficam restritas a um único módulo.

**Segurança** envolve proteção contra acesso, alteração, exposição ou interrupção indevidos. Criptografia de banco de dados pode fazer parte da segurança, mas segurança também envolve autenticação, autorização, gestão de segredos, validação de entradas, proteção de comunicação, auditoria e várias outras medidas.

**Acessibilidade** é a capacidade de permitir uso por pessoas com diferentes necessidades, incluindo limitações visuais, auditivas, motoras, cognitivas e outras. Ela não se restringe a impedimentos físicos.

**Arquivabilidade** envolve regras sobre preservação, retenção, arquivamento e exclusão de dados ao longo do tempo.

**Autenticação** busca confirmar a identidade de um usuário ou sistema: "quem é você?".

**Autorização** determina o que uma identidade autenticada pode fazer: "a que você tem acesso?".

**Privacidade** envolve tratamento adequado de dados pessoais ou sensíveis, incluindo coleta, acesso, exposição, retenção e compartilhamento.

**Conformidade legal** trata das normas e obrigações jurídicas que limitam ou orientam o funcionamento do sistema.

**Usabilidade** está relacionada à capacidade de os usuários atingirem seus objetivos com eficácia, eficiência e um nível adequado de esforço e aprendizagem.

## Requisitos de domínio e características arquiteturais

Uma solução de software precisa atender tanto às regras do **domínio do problema** quanto às características de qualidade esperadas.

Em um sistema bancário, por exemplo, "transferir dinheiro entre contas" é uma capacidade do domínio. Já "uma transferência deve ser autenticada, auditável e processada em determinado tempo" introduz características que afetam a arquitetura.

Essas características alteram decisões estruturais. Um sistema que precisa atender poucos usuários internos pode ser organizado de forma diferente de um serviço público que precisa continuar disponível mesmo durante picos de milhões de acessos.

## Trade-offs

Arquitetura envolve **trade-offs** porque melhorar uma característica pode aumentar custo, complexidade ou pressão sobre outra característica. Não existe uma configuração que maximize simultaneamente todos os atributos possíveis.

Um exemplo é **segurança versus desempenho**. Mecanismos de segurança podem acrescentar trabalho ao processamento. Criptografar e descriptografar dados consome recursos; verificar autenticação e autorização exige processamento; registrar eventos de auditoria acrescenta escrita e armazenamento; funções de derivação de senha são deliberadamente computacionalmente caras para dificultar ataques.

Isso não significa que a solução seja simplesmente retirar segurança para deixar o sistema rápido. A decisão arquitetural consiste em atender ao nível de segurança necessário e projetar a solução para que o custo seja aceitável, utilizando técnicas adequadas de implementação, dimensionamento e infraestrutura.

Outro exemplo aparece em **desempenho versus consistência**. Um cache pode reduzir tempo de resposta, mas aumenta a dificuldade de garantir que o usuário esteja sempre vendo o dado mais recente.

Também pode haver **disponibilidade versus custo**: manter redundância em várias máquinas ou regiões aumenta a tolerância a falhas, mas exige mais infraestrutura e operação.

Assim, arquitetura não consiste em escolher isoladamente "o melhor atributo". Ela exige explicitar quais qualidades são prioritárias para aquele sistema e quais custos e riscos são aceitáveis.

Boa parte desses conceitos reaparece em outra escala no conteúdo de Programação Modular. Modularidade, acoplamento, extensibilidade e manutenção já surgiram quando estudamos como organizar classes e módulos. Arquitetura amplia o mesmo tipo de preocupação para o sistema como um todo.

Em Programação Modular, podemos perguntar se duas classes estão excessivamente acopladas. Em arquitetura, podemos perguntar a mesma coisa sobre módulos, serviços, bancos de dados ou sistemas inteiros.

## Pontos que costumam gerar confusão

- **Arquitetura não é simplesmente a lista de tecnologias utilizadas.** Node.js, ASP.NET, PostgreSQL ou um framework podem participar da implementação, mas não descrevem sozinhos a arquitetura.
- **Um sistema possui uma arquitetura, mas essa arquitetura pode combinar vários estilos e ser documentada por várias visões.**
- **Cliente e servidor são papéis na comunicação.** Eles não precisam necessariamente estar em equipamentos físicos diferentes.
- **O servidor não devolve sempre HTML, CSS e JavaScript juntos.** Cada resposta HTTP pode transportar um tipo de recurso, e o navegador normalmente faz requisições separadas para os recursos de uma página.
- **Back-end não é sinônimo de banco de dados.** O banco pode ser uma parte da solução; o back-end também implementa regras, validações, autenticação, integração e geração de respostas.
- **Segurança é maior do que criptografia.** Criptografia é apenas um dos mecanismos possíveis.
- **Acessibilidade não se limita a deficiência física.**
- **Escalabilidade e elasticidade são relacionadas, mas diferentes.** Escalabilidade trata da capacidade de suportar crescimento; elasticidade trata do ajuste de recursos de acordo com a demanda.
- **Características arquiteturais não possuem uma classificação universal.** Diferentes autores e organizações usam taxonomias diferentes.
