# Mapeamento de entidades e atributos: do DER ao esquema relacional

> **Contexto:** Sessão da PUC Minas sobre a passagem do Diagrama Entidade-Relacionamento para o modelo relacional. O foco está nas regras de mapeamento de entidades regulares, atributos compostos e multivalorados e entidades fracas, conectando o projeto conceitual ao projeto lógico.

---

## Introdução

Até aqui, o DER serviu para representar o mini-mundo em termos de entidades, atributos, relacionamentos, cardinalidades e restrições. Essa representação ainda não é, por si só, o esquema de tabelas que será implementado em um banco relacional.

O **mapeamento relacional** é o conjunto de regras usado para transformar elementos do modelo conceitual em estruturas do modelo relacional. A pergunta muda de forma:

> no DER, perguntamos "quais objetos e regras existem no domínio?"; no projeto lógico, perguntamos "como essas regras serão representadas por relações, atributos, chaves primárias e chaves estrangeiras?".

Esta sessão retoma diretamente [[04. Níveis do sgbd e etapas do projeto de banco de dados]]. Antes, vimos a esteira inteira. Agora estamos ampliando apenas a passagem entre duas etapas: **projeto conceitual → projeto lógico**.

---

## 1. Retomando projeto conceitual, lógico e físico

As três etapas não descrevem três bancos diferentes. Elas descrevem níveis sucessivos de decisão sobre o mesmo problema.

| Etapa | Pergunta central | Resultado | Dependência tecnológica |
| :--- | :--- | :--- | :--- |
| **Projeto conceitual** | Quais dados e regras existem no mini-mundo? | DER/MER com entidades, atributos e relacionamentos | Independente do paradigma e de um SGBD específico |
| **Projeto lógico** | Como esse modelo será representado em uma classe de banco de dados? | Esquema relacional com relações, atributos, PKs e FKs | Vinculado ao modelo relacional, mas ainda não a um produto específico |
| **Projeto físico** | Como esse esquema será implementado e otimizado em um produto concreto? | Estruturas, tipos, índices e decisões de armazenamento | Específico para PostgreSQL, SQL Server, Oracle etc. |

A anotação de aula "projeto lógico: esquema lógico para uma classe de BD" está correta se entendermos **classe** como o paradigma ou modelo de dados escolhido. Neste caso, a classe é a dos bancos relacionais.

Há também uma distinção útil: os termos "conceitual", "lógico" e "físico" aparecem tanto nas etapas de projeto quanto em discussões de níveis de abstração do SGBD. As ideias se relacionam, mas não são exatamente a mesma classificação. Nesta sessão, estamos falando das **etapas do projeto de banco de dados**.

---

## 2. O que significa mapear

Mapear não significa copiar o desenho do DER para tabelas de forma mecânica. Alguns elementos podem ser convertidos quase diretamente, enquanto outros precisam mudar de estrutura.

Uma entidade regular costuma originar uma relação. Um atributo composto é decomposto em seus componentes simples. Um atributo multivalorado precisa de outra relação. Uma entidade fraca recebe a chave da entidade proprietária para formar sua própria identificação no modelo relacional.

O modelo conceitual preserva a semântica do domínio. O mapeamento precisa preservar essa mesma semântica usando as regras permitidas pelo modelo relacional.

---

## 3. Mapeamento de entidade regular

Uma **entidade regular**, também chamada de entidade forte, possui identificação própria. A regra básica é:

> para cada entidade regular do DER, criar uma relação no modelo relacional contendo seus atributos simples e os componentes simples de seus atributos compostos.

Considere a entidade conceitual **CLIENTE** com:

* código do cliente;
* nome;
* endereço, composto por logradouro, número, bairro e cidade.

O resultado lógico pode ser representado como:

**CLIENTE(CodCliente, Nome, Logradouro, Numero, Bairro, Cidade)**

O atributo composto **Endereco** não precisa virar uma coluna adicional chamada "Endereco" se seus componentes já representam a informação necessária. O mapeamento normalmente leva os componentes simples para a relação.

### Escolha da chave primária

A formulação "escolher um dos atributos para ser chave primária" precisa de uma pequena correção.

O projetista escolhe uma **chave candidata** para ser a PK. Essa chave pode ser:

* um único atributo, como **CodCliente**;
* uma combinação de atributos, quando a identificação for composta.

Portanto, não existe uma regra dizendo que a PK precisa ser sempre uma única coluna.

### E os "atributos fracos"?

"Atributo fraco" não é uma categoria padrão da modelagem estudada. A provável associação é com a **chave parcial** de uma entidade fraca.

Os tipos de atributos continuam sendo simples, compostos, multivalorados, derivados, identificadores etc. Uma entidade fraca pode ter esses mesmos tipos de atributos. O que muda é a forma como sua **identidade** é construída.

---

## 4. O que acontece com atributos derivados

Um atributo derivado, como **idade** calculada a partir de **data_nascimento**, normalmente não precisa ser copiado para a relação como dado armazenado.

Isso não é uma proibição absoluta. Um sistema pode decidir materializar um valor calculado por razões de desempenho ou histórico. Essa já é uma decisão de projeto e implementação, com custos de sincronização.

Como regra de mapeamento inicial:

> se o valor puder ser obtido de forma confiável a partir de outros dados, ele pode permanecer derivado em vez de ser persistido como uma coluna comum.

Isso retoma a distinção feita em [[05. Modelagem de entidades e tipos de atributos]].

---

## 5. Mapeamento de atributo multivalorado

Um atributo multivalorado pode assumir vários valores para a mesma ocorrência da entidade. O exemplo clássico é um cliente com vários telefones.

No DER podemos ter:

**CLIENTE**
* CodCliente
* Nome
* Telefones {Telefone}

No modelo relacional, colocar vários telefones dentro de uma única célula, como "3199999, 3188888, 3177777", dificultaria a aplicação das operações e restrições relacionais.

A solução é criar uma nova relação:

**CLIENTE(CodCliente, Nome)**

**TELEFONE_CLIENTE(CodCliente, Telefone)**

Nessa nova relação:

* **CodCliente** é uma FK que referencia a PK de **CLIENTE**;
* **Telefone** armazena um valor do conjunto multivalorado por tupla;
* uma escolha comum de PK é **(CodCliente, Telefone)**, impedindo que o mesmo telefone seja repetido duas vezes para o mesmo cliente.

A ideia de "valor atômico" merece precisão. No modelo relacional e na primeira forma normal, cada posição da relação deve conter um único valor do domínio definido para aquele atributo. O que conta como indivisível depende do domínio escolhido. O ponto relevante aqui é que uma célula não deve funcionar como uma lista de vários telefones independentes.

### Modelo mental

A entidade **CLIENTE** continua representando uma pessoa ou organização. A tabela de telefones funciona como uma coleção de linhas subordinadas ao cliente:

| CodCliente | Telefone |
| :--- | :--- |
| C1 | 31 99999-1111 |
| C1 | 31 98888-2222 |
| C2 | 11 97777-3333 |

A repetição de **C1** é esperada. Cada linha representa um telefone diferente do mesmo cliente.

---

## 6. Atributo multivalorado não é entidade fraca

Os dois casos podem produzir uma nova tabela no projeto lógico, mas a razão é diferente.

No atributo multivalorado, criamos uma relação porque uma entidade pode possuir vários valores daquele atributo.

Na entidade fraca, criamos uma relação porque existe um tipo de entidade com atributos próprios cuja **identificação depende de outra entidade**.

Essa diferença é importante: duas regras de mapeamento podem chegar a estruturas parecidas sem representarem o mesmo conceito no DER.

---

## 7. Mapeamento de entidade fraca

Uma entidade fraca não possui uma chave completa capaz de identificá-la de forma independente. Ela possui uma **chave parcial**, também chamada de discriminador, que só distingue ocorrências dentro de uma mesma entidade proprietária.

Considere o exemplo de [[07. Modelo de entidades e relacionamentos estendido]]:

**BANCO**
* CodigoBanco, identificador
* Nome

**AGENCIA**
* NumAgencia, chave parcial
* Endereco

Uma agência de número 1045 pode existir em bancos diferentes. Portanto:

**NumAgencia = 1045**

não identifica globalmente uma agência.

A identificação completa exige:

**CodigoBanco + NumAgencia**

---

## 8. Regra de mapeamento da entidade fraca

Para cada entidade fraca ligada a sua entidade proprietária:

1. criar uma relação para a entidade fraca;
2. incluir seus atributos simples e os componentes simples dos atributos compostos;
3. incluir na nova relação os atributos que formam a PK da entidade proprietária;
4. declarar esses atributos herdados da proprietária como FK;
5. formar a PK da entidade fraca pela combinação entre a PK da proprietária e a chave parcial da entidade fraca.

O resultado do exemplo fica:

**BANCO(CodigoBanco, Nome)**

PK de BANCO: **CodigoBanco**

**AGENCIA(CodigoBanco, NumAgencia, Endereco)**

FK de AGENCIA: **CodigoBanco → BANCO.CodigoBanco**

PK de AGENCIA: **(CodigoBanco, NumAgencia)**

---

## 9. Por que a chave da proprietária vira FK?

Esse é o primeiro dos dois pontos que costuma parecer arbitrário.

A tabela **AGENCIA** precisa registrar a qual banco cada agência pertence. Para isso, ela recebe o valor de **CodigoBanco**.

Esse atributo possui duas funções simultâneas:

* como **FK**, aponta para a ocorrência proprietária em **BANCO**;
* como parte da identificação de **AGENCIA**, informa o contexto dentro do qual **NumAgencia** é único.

Sem **CodigoBanco**, a linha da agência saberia que é "1045", mas não saberia de qual banco é a agência 1045.

---

## 10. Por que a PK da entidade fraca é composta?

A chave parcial é apenas parcialmente identificadora.

Imagine:

| CodigoBanco | NumAgencia | Endereco |
| :--- | :--- | :--- |
| B1 | 1045 | Belo Horizonte |
| B2 | 1045 | São Paulo |
| B1 | 2030 | Contagem |

**NumAgencia = 1045** aparece duas vezes e isso não é um erro. As duas agências pertencem a bancos diferentes.

A combinação é que precisa ser única:

* **(B1, 1045)**
* **(B2, 1045)**
* **(B1, 2030)**

Portanto, a PK relacional da entidade fraca é formada por:

> **PK da proprietária + chave parcial da fraca**

A entidade fraca não tinha uma chave completa própria no DER. Depois do mapeamento, a tabela resultante passa a possuir uma PK válida, construída com a identidade da proprietária.

---

## 11. Como reconhecer a notação no DER de Chen

A dúvida sobre "borda dupla" envolve símbolos diferentes que usam o mesmo recurso gráfico.

| Elemento | Representação em Chen | Significado |
| :--- | :--- | :--- |
| Entidade regular | Retângulo simples | Entidade com identificação própria |
| Entidade fraca | **Retângulo duplo** | Entidade com identificação dependente |
| Relacionamento identificador | **Losango duplo** | Relacionamento usado para identificar a entidade fraca |
| Atributo multivalorado | **Elipse dupla** | Atributo que pode assumir vários valores |
| Chave parcial | Nome com **sublinhado tracejado** | Discriminador da entidade fraca |
| Atributo derivado | Elipse com **borda tracejada** | Valor calculado a partir de outros dados |
| Participação total | Linha dupla | Toda ocorrência precisa participar do relacionamento |

Então, sim: atributo multivalorado e entidade fraca usam contorno duplo, mas em **formas diferentes** e com significados diferentes.

O tracejado também aparece em duas situações distintas:

* **sublinhado tracejado**: chave parcial;
* **borda tracejada da elipse**: atributo derivado.

---

## 12. As três regras lado a lado

| Elemento do DER | Transformação principal | Chave no modelo relacional |
| :--- | :--- | :--- |
| **Entidade regular** | Cria uma relação com atributos simples e componentes simples dos compostos | Uma chave candidata é escolhida como PK |
| **Atributo multivalorado** | Cria uma nova relação contendo a PK da entidade proprietária e o valor do atributo | Frequentemente PK composta pela FK da proprietária + valor multivalorado |
| **Entidade fraca** | Cria uma relação contendo seus atributos e a PK da entidade proprietária | PK composta pela PK da proprietária + chave parcial |

A semelhança entre os dois últimos casos é útil, mas não deve apagar a diferença semântica.

---

## 13. Onde entram as restrições de integridade

O mapeamento já cria estruturas que dependem das quatro integridades vistas em [[09. Integridade referencial e chave estrangeira]].

No caso de **TELEFONE_CLIENTE**:

* a integridade de domínio define quais valores são válidos para **Telefone**;
* a integridade de entidade exige que os componentes da PK estejam preenchidos;
* a integridade de chave impede repetir a mesma combinação **(CodCliente, Telefone)**;
* a integridade referencial exige que **CodCliente** corresponda a um cliente existente.

No caso de **AGENCIA**:

* **CodigoBanco** precisa apontar para um banco existente;
* **CodigoBanco + NumAgencia** precisa ser único;
* como ambos formam a PK, nenhum dos dois pode ser nulo.

O mapeamento e as integridades são, portanto, duas partes do mesmo projeto lógico: primeiro definimos a estrutura; depois garantimos que apenas estados válidos possam existir nela.

---

## 14. Onde entram CASCADE, SET NULL e outras ações

As ações referenciais não são uma quarta regra de mapeamento. Elas definem **o que o SGBD deve fazer quando uma chave referenciada é alterada ou excluída**.

Por isso, faz sentido tratá-las depois de identificar corretamente PKs e FKs.

Em uma entidade fraca, **ON DELETE CASCADE** pode ser coerente com a dependência de existência: apagar a entidade proprietária pode apagar também suas ocorrências dependentes. Entretanto, o fato de uma entidade ser fraca **não obriga automaticamente** o uso de CASCADE. A ação escolhida depende da regra do sistema.

Há uma consequência importante:

> se a FK da proprietária também faz parte da PK da entidade fraca, **SET NULL** normalmente não é compatível com essa identificação, porque componentes de uma PK não podem ser nulos.

**RESTRICT** ou **NO ACTION** podem ser escolhidos quando o sistema deve impedir a exclusão da proprietária enquanto existirem dependentes.

**ON UPDATE CASCADE** pode propagar uma mudança na chave proprietária para as relações dependentes. Na prática, chaves primárias bem escolhidas tendem a ser estáveis, então atualizar uma PK costuma ser menos comum do que excluir uma ocorrência.

As diferenças entre essas ações estão detalhadas em [[09. Integridade referencial e chave estrangeira]].

---

## 15. Um detalhe importante sobre dependência de existência

Entidade fraca e FK não são sinônimos.

Toda tabela resultante de uma entidade fraca terá uma ligação identificadora com a tabela proprietária. Porém, uma tabela pode possuir FK sem representar uma entidade fraca.

Por exemplo, **EMPREGADO** pode ter sua própria PK **CodEmp** e uma FK **CodigoDepto**. O empregado continua possuindo uma identidade própria. A FK apenas registra seu relacionamento com o departamento.

Já **AGENCIA**, no exemplo estudado, depende de **CodigoBanco** para completar sua própria identidade.

A pergunta de controle é:

> a chave da outra entidade é necessária apenas para representar uma associação ou é necessária para completar a própria identificação desta ocorrência?

Se for necessária para completar a identificação, estamos diante do padrão de entidade fraca.

## 16. Modelo mental para prova

| Pergunta | Resposta curta |
| :--- | :--- |
| O que acontece com uma entidade regular? | Vira uma relação com seus atributos mapeáveis. |
| A PK precisa ser uma única coluna? | Não. Escolhe-se uma chave candidata, que pode ser composta. |
| O que acontece com um atributo composto? | Seus componentes simples viram atributos da relação. |
| O que acontece com um atributo multivalorado? | Vira uma nova relação ligada por FK à entidade proprietária. |
| Existe "atributo fraco"? | Não como categoria padrão. O conceito próximo é chave parcial de entidade fraca. |
| O que acontece com uma entidade fraca? | Vira relação e recebe a PK da proprietária como FK. |
| Como se forma sua PK? | PK da proprietária + chave parcial da entidade fraca. |
| Multivalorado tem borda dupla? | Sim, elipse dupla. |
| Entidade fraca tem borda dupla? | Sim, retângulo duplo. |
| O que o tracejado indica? | Sublinhado tracejado para chave parcial; elipse tracejada para atributo derivado. |
| CASCADE faz parte do mapeamento? | Não. É uma ação de integridade referencial definida para a FK. |
| Entidade fraca exige ON DELETE CASCADE? | Não. Pode ser coerente, mas é uma decisão do esquema. |

A sequência mais útil para memorizar é:

**DER → identificar o tipo de elemento → aplicar a regra de mapeamento → definir PK/FK → aplicar restrições de integridade**

---

## 17. Pontos que costumam gerar confusão

**Entidade regular não significa "tabela sem FK".** Uma entidade forte pode ter identidade própria e, ao mesmo tempo, participar de relacionamentos que resultem em FKs.

**Atributo multivalorado não vira várias colunas como Telefone1, Telefone2 e Telefone3.** Essa solução fixa artificialmente uma quantidade máxima e dificulta a manipulação dos dados.

**Entidade fraca não fica sem PK no modelo relacional.** Ela não possui uma chave completa própria no DER, mas a tabela resultante recebe uma PK composta.

**A chave parcial não é globalmente única.** Ela só precisa distinguir as ocorrências que pertencem à mesma entidade proprietária.

**A FK copiada da proprietária pode fazer parte da PK da fraca.** Nesse caso, a mesma coluna participa simultaneamente da integridade referencial e da identificação da tupla.

**CASCADE não deve ser aplicado por hábito.** Ele expressa uma regra de ciclo de vida dos dados e pode gerar exclusões em cadeia.
