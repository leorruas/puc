# Consultas dependentes, `any` e `all` em coleções

> **Contexto:** Operações como “existe algum?”, “todos atendem?” e “filtre um item usando informações de outra coleção” também aparecem em linguagens de programação. A analogia ajuda a reconhecer o padrão mental de subconsultas SQL, mas não reproduz automaticamente a estratégia de execução de um SGBD.

## Consultas dependentes filtram uma coleção a partir de outra

Três perguntas aparecem repetidamente:

| Pergunta | SQL | Coleções em código |
| --- | --- | --- |
| existe pelo menos um elemento que satisfaz a condição? | `EXISTS` | `Any`, `any`, `some` |
| todos os elementos satisfazem a condição? | `ALL` com comparação | `All`, `all`, `every` |
| o filtro de um elemento depende de outra coleção? | subconsulta correlacionada | predicado que consulta outra coleção |

A ponte parte do [[03. Manipulação de Dados SQL/11. Consultas aninhadas sem e com correlação|artigo 11 de Manipulação de dados com SQL]].

## C#: LINQ

Verificar se existe algum valor:

~~~csharp
bool existe = alugueis.Any(a => a.CustomerId == cliente.Id);
~~~

Verificar se todos satisfazem uma condição:

~~~csharp
bool todosPagaram = pagamentos.All(p => p.Valor > 0);
~~~

Filtrar produtos comparando cada item com a média de sua própria categoria:

~~~csharp
var resultado = produtos
    .Where(p =>
        p.Preco < produtos
            .Where(p2 => p2.CategoriaId == p.CategoriaId)
            .Average(p2 => p2.Preco)
    );
~~~

A expressão interna depende do produto externo `p`, assim como uma subconsulta correlacionada depende da linha da consulta externa.

## Java: streams

Existência:

~~~java
boolean existe = alugueis.stream()
    .anyMatch(a -> a.getCustomerId() == cliente.getId());
~~~

Todos:

~~~java
boolean todosPagaram = pagamentos.stream()
    .allMatch(p -> p.getValor() > 0);
~~~

Filtro dependente de outra consulta sobre a coleção:

~~~java
var resultado = produtos.stream()
    .filter(p -> {
        double media = produtos.stream()
            .filter(p2 -> p2.getCategoriaId() == p.getCategoriaId())
            .mapToDouble(Produto::getPreco)
            .average()
            .orElse(0);

        return p.getPreco() < media;
    })
    .toList();
~~~

## Python

Existência:

~~~python
existe = any(
    aluguel["customer_id"] == cliente["id"]
    for aluguel in alugueis
)
~~~

Todos:

~~~python
todos_pagaram = all(
    pagamento["valor"] > 0
    for pagamento in pagamentos
)
~~~

Filtro dependente da categoria do item atual:

~~~python
resultado = []

for produto in produtos:
    mesma_categoria = [
        p for p in produtos
        if p["categoria_id"] == produto["categoria_id"]
    ]

    media = sum(p["preco"] for p in mesma_categoria) / len(mesma_categoria)

    if produto["preco"] < media:
        resultado.append(produto)
~~~

## JavaScript

Existência:

~~~javascript
const existe = alugueis.some(
  a => a.customerId === cliente.id
);
~~~

Todos:

~~~javascript
const todosPagaram = pagamentos.every(
  p => p.valor > 0
);
~~~

Filtro dependente de outra seleção sobre o mesmo array:

~~~javascript
const resultado = produtos.filter(produto => {
  const mesmaCategoria = produtos.filter(
    p => p.categoriaId === produto.categoriaId
  );

  const media =
    mesmaCategoria.reduce((soma, p) => soma + p.preco, 0) /
    mesmaCategoria.length;

  return produto.preco < media;
});
~~~

## Comparação entre `any`, `all` e filtros dependentes

| Intenção | C# | Java | Python | JavaScript |
| --- | --- | --- | --- | --- |
| existe algum? | `Any` | `anyMatch` | `any` | `some` |
| todos? | `All` | `allMatch` | `all` | `every` |
| filtro dependente | `Where` dentro de `Where` | stream dentro de `filter` | laço/compreensão dependente | `filter` dentro de `filter` |

> **Precisão conceitual:** SQL `ANY` não é simplesmente o mesmo operador que `any()`, `Any()`, `anyMatch()` ou `some()`. Em SQL, `ANY` aparece combinado com um operador de comparação, como `> ANY (subconsulta)`. A semelhança útil está na lógica de “basta uma ocorrência satisfazer a condição”.

## Pontos que costumam gerar confusão

- **`EXISTS` se aproxima da pergunta “existe algum?”, mas a execução no SGBD não deve ser imaginada como um loop literal em memória.**
- **SQL `ALL` aparece ligado a uma comparação.** As funções `all`/ `All`/ `allMatch`/ `every` recebem um predicado diretamente.
- **Uma consulta dependente pode recalcular informações para cada item externo.** Esse é o paralelo mental mais útil com subconsultas correlacionadas.
- **A analogia ajuda no raciocínio, mas SQL continua operando sobre relações e o SGBD escolhe seu plano de execução.**
