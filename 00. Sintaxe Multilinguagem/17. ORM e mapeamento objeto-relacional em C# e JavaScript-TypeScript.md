# ORM e mapeamento objeto-relacional em C# e JavaScript/TypeScript

> **Contexto:** Esta nota compara como o conceito de ORM aparece no ecossistema C#/.NET e em back-ends JavaScript/TypeScript. O objetivo é separar o conceito de ORM da linguagem ou do framework de interface e mostrar como entidades, relações, chaves estrangeiras, consultas e persistência aparecem em ferramentas diferentes.

## ORM não é uma coisa específica do C#

**ORM (Object-Relational Mapping)** é uma técnica para fazer a ponte entre:

- objetos e tipos usados no código;
- tabelas, colunas, chaves e relacionamentos de um banco relacional.

O Entity Framework Core é um ORM do ecossistema .NET, mas a mesma ideia aparece em outras linguagens e ferramentas.

O conceito permanece:

`objetos/tipos no código ↔ ORM ↔ modelo relacional`

O que muda é **como cada ferramenta descreve esse mapeamento**.

## React não possui um ORM próprio

**React é uma biblioteca de interface**. Ele organiza componentes e estado da interface no cliente; não é a camada responsável por mapear objetos para tabelas de um banco relacional.

Em uma arquitetura comum:

`React no navegador → API/backend → ORM → banco de dados`

O ORM costuma estar no **backend**, onde o código possui acesso seguro às credenciais e à conexão com o banco.

Em um projeto JavaScript ou TypeScript, esse backend pode executar em Node.js. Alguns ecossistemas full-stack permitem escrever código de servidor no mesmo projeto que contém React, mas o ORM continua executando **no lado do servidor**, não dentro do componente React enviado ao navegador.

Portanto:

- **React** → interface e interação;
- **Node.js/backend** → lógica de servidor;
- **ORM** → mapeamento e acesso ao banco relacional.

## O equivalente conceitual ao EF Core em JavaScript/TypeScript

Não existe um único “EF Core do JavaScript”. Há diferentes ferramentas com propostas próprias.

Exemplos:

| Ecossistema | Ferramenta | Como o mapeamento costuma aparecer |
| --- | --- | --- |
| C# / .NET | Entity Framework Core | Classes C#, `DbContext`, `DbSet<T>`, convenções, Data Annotations e Fluent API |
| JavaScript/TypeScript | Prisma ORM | Modelo declarado em um arquivo de schema e cliente gerado para consultas |
| TypeScript | TypeORM | Classes e decorators para entidades e relacionamentos |
| JavaScript/TypeScript | Sequelize | Models e associações configurados pela API da biblioteca |

Todas resolvem, com diferenças de API e arquitetura, a mesma família de problemas: representar entidades, relacionamentos e operações persistentes sem escrever manualmente todo o SQL de cada operação.

## EF Core: relação 1:N por classes e convenção

O exemplo completo e sua explicação conceitual estão em [[05. Desenvolvimento Web Back-End/05. Frameworks Web, MVC e mapeamento objeto-relacional#Relacionamento 1:N: gênero e filme|Relacionamento 1:N com EF Core]].

No EF Core:

```csharp
public class Genero
{
    public int Id { get; set; }
    public string Descricao { get; set; } = string.Empty;

    public ICollection<Filme> Filmes { get; set; }
        = new List<Filme>();
}

public class Filme
{
    public int Id { get; set; }
    public string Titulo { get; set; } = string.Empty;

    public int GeneroId { get; set; }
    public Genero Genero { get; set; } = null!;
}
```

O EF Core consegue reconhecer por **convenção** que:

- `Filme.Genero` é uma propriedade de navegação;
- `Filme.GeneroId` pode funcionar como chave estrangeira correspondente;
- `Genero.Filmes` representa o lado “muitos”.

Nesse caso, escrever:

```csharp
[ForeignKey(nameof(GeneroId))]
public Genero Genero { get; set; } = null!;
```

pode tornar a intenção explícita, mas não é obrigatório se o relacionamento já puder ser inferido pelas convenções.

A ideia importante é:

> **convenção** = a ferramenta reconhece o mapeamento pela estrutura e pelos nomes esperados.

> **configuração explícita** = o desenvolvedor declara diretamente como o relacionamento deve ser interpretado.

## Prisma: o relacionamento fica explícito no schema

Em Prisma, o modelo relacional é normalmente declarado em `schema.prisma`:

```prisma
model Genero {
  id        Int     @id @default(autoincrement())
  descricao String
  filmes    Filme[]
}

model Filme {
  id       Int    @id @default(autoincrement())
  titulo   String
  generoId Int
  genero   Genero @relation(fields: [generoId], references: [id])
}
```

Depois, o código TypeScript usa o cliente gerado:

```typescript
const filme = await prisma.filme.findUnique({
  where: { id: 42 },
  include: { genero: true }
});
```

A diferença de estilo é importante:

- EF Core parte fortemente das classes C# e consegue inferir vários mapeamentos por convenção;
- Prisma mantém uma declaração de modelo própria e gera uma API tipada para o código JavaScript/TypeScript.

## TypeORM: entidades e decorators

TypeORM se aproxima mais visualmente do estilo com atributos do .NET porque usa classes TypeScript e decorators.

```typescript
@Entity()
class Filme {
  @PrimaryGeneratedColumn()
  id: number;

  @Column()
  titulo: string;

  @ManyToOne(() => Genero, genero => genero.filmes)
  genero: Genero;
}
```

A sintaxe é diferente, mas o papel conceitual é semelhante:

- identificar uma entidade;
- descrever propriedades persistentes;
- declarar um relacionamento;
- permitir que o ORM transforme operações em comandos para o banco.

## O que seria parecido com `DbContext` e `DbSet<T>`?

As APIs não possuem equivalência perfeita, mas é possível construir uma aproximação conceitual:

| EF Core | Outro ecossistema | Ideia aproximada |
| --- | --- | --- |
| `DbContext` | Prisma Client / DataSource do TypeORM | Objeto central usado para acessar e coordenar operações persistentes |
| `DbSet<Filme>` | `prisma.filme` / Repository de `Filme` | Ponto de entrada tipado para operações sobre uma entidade |
| `Find(42)` | `findUnique(...)` / `findOne(...)` | Buscar uma entidade |
| `Add(...)` + `SaveChanges()` | `create(...)` ou `save(...)` | Inserir/persistir uma entidade |
| Migration do EF Core | Prisma Migrate / migrations do TypeORM | Evoluir o esquema do banco |

Essa tabela é apenas uma comparação de **responsabilidades**, não uma equivalência exata de APIs.

## Onde a chave estrangeira continua existindo?

Independentemente do ORM, o banco relacional ainda possui uma relação concreta.

Para:

`Genero 1 → N Filme`

o modelo relacional continua podendo ter:

```text
Generos
- Id (PK)
- Descricao

Filmes
- Id (PK)
- Titulo
- GeneroId (FK → Generos.Id)
```

O ORM muda a forma como o código trabalha com essa estrutura; ele não elimina chave estrangeira, cardinalidade ou integridade referencial.

Essa conexão pode ser aprofundada em [[02. Modelagem de Dados/11. Mapeamento de relacionamentos#Relacionamentos binários: 1:1, 1:N e N:N|Mapeamento de relacionamento 1:N]].

## Convenção versus configuração explícita

Uma das diferenças mais importantes entre ORMs é **quanto eles inferem automaticamente** e **quanto exigem declaração explícita**.

| Estratégia | Exemplo | Vantagem | Cuidado |
| --- | --- | --- | --- |
| Convenção | EF Core reconhece `GeneroId` associado a `Genero` | Menos configuração repetitiva | É preciso conhecer as convenções |
| Data Annotation/decorator | `[ForeignKey]`, `@ManyToOne` | Mapeamento fica visível perto da classe | Pode acoplar a classe à ferramenta |
| Schema/configuração própria | relações em Prisma Schema | Modelo persistente fica explicitamente descrito | Existe uma linguagem/configuração adicional |
| Fluent/API programática | Fluent API do EF Core ou APIs de associação | Permite configurações mais complexas | A configuração pode ficar distante da entidade |

Por isso, ao trocar de ORM, a pergunta útil não é apenas “qual é o equivalente de `[ForeignKey]`?”, mas:

> **onde esta ferramenta declara o relacionamento e quais partes ela consegue inferir por convenção?**

## ORM conecta objetos, mapeamento e esquema relacional

Se a interface for React com um backend Node.js:

```text
React
  ↓ HTTP
backend JavaScript/TypeScript
  ↓
Prisma / TypeORM / Sequelize
  ↓
PostgreSQL / MySQL / SQL Server / outro banco relacional
```

Se a aplicação for ASP.NET Core MVC:

```text
View / Controller
  ↓
Entity Framework Core
  ↓
SQL Server / SQLite / PostgreSQL / outro provider
```

A tecnologia muda; o conceito permanece:

**o ORM fica entre o modelo de objetos usado pela aplicação e o modelo relacional do banco.**
