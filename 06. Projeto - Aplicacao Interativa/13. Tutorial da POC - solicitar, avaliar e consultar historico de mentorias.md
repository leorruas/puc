# Tutorial da POC: solicitar, avaliar e consultar histórico de mentorias

> **Projeto:** NODO  
> **Recorte da dupla:** Leonardo Ruas Santos + Samuel Campos Salema  
> **Casos de uso deste tutorial:** Solicitar mentoria, Avaliar mentoria e Consultar histórico de mentorias  
> **Objetivo imediato:** produzir uma POC real da aplicação, aproveitável na Etapa 03  
> **Ambiente principal deste tutorial:** macOS Apple Silicon + Antigravity IDE + .NET CLI + ASP.NET Core MVC + Entity Framework Core + Azure SQL / SQL Server

---

## 1. O que vamos construir

A POC não deve ser tratada como um projeto descartável. A orientação mais recente do Grupo 4 é aproveitar a atividade individual para implementar um caso de uso real do NODO que depois ficará sob responsabilidade do próprio integrante.

Para a dupla Leonardo + Samuel, este tutorial assume três casos de uso relacionados:

1. **Solicitar mentoria:** o estudante escolhe um horário disponível, informa o objetivo da sessão e cria uma solicitação com status pendente.
2. **Consultar histórico de mentorias:** o estudante visualiza sessões anteriores e seus registros associados.
3. **Avaliar mentoria:** após uma sessão concluída, o estudante registra nota de 1 a 5 e comentário.

Esses três fluxos usam o mesmo núcleo de domínio: **Mentoria**. A solicitação cria o registro, o histórico consulta registros e a avaliação acrescenta um registro relacionado a uma mentoria concluída.

### Ordem recomendada

A implementação deve seguir esta ordem:

**Solicitar mentoria → Consultar histórico → Avaliar mentoria**

A razão é técnica. Solicitar mentoria é o fluxo que melhor prova a arquitetura completa da POC:

**View → Controller → regra de negócio → Entity Framework Core → SQL Server → resposta para a View**

O histórico reaproveita os mesmos dados como leitura. A avaliação acrescenta uma segunda entidade relacionada à mentoria.

## 3. Definir quem será dono de qual POC individual

Embora Leonardo e Samuel estejam no mesmo bloco funcional, a POC é individual. Portanto, cada um deve ter um caso de uso pelo qual consiga responder de ponta a ponta.

Uma divisão inicial possível é:

- **Leonardo:** Solicitar mentoria;
- **Samuel:** Avaliar mentoria;
- **Consultar histórico:** integração comum da dupla, podendo ser assumida por quem estiver com menos carga ou ser conectada após as duas POCs.

Solicitar mentoria depende de coisas que podem estar sob responsabilidade de outros integrantes:

- usuário autenticado;

Para a POC, podemos assumir temporariamente:

# Fase 3: preparar o SQL Server no Mac M1

## 12. Não usar SQL Server local em Docker como primeira opção

No Apple Silicon, o caminho mais simples pode parecer executar SQL Server em Docker com emulação x86. Para este projeto, não recomendo transformar isso no ambiente principal.

As imagens oficiais de SQL Server para Linux são documentadas pela Microsoft para hosts x86-64. Emulação por Rosetta/QEMU não é uma configuração oficialmente suportada.

Para o Mac M1, a opção mais limpa é:

**ASP.NET Core local no Mac + SQL Server remoto no Azure SQL.**

Isso mantém a stack SQL Server exigida pelo projeto sem obrigar o Mac a emular um servidor x86.

## 13. Criar um Azure SQL Database para desenvolvimento

Entre no Azure com sua conta acadêmica.

A Microsoft atualmente oferece uma opção gratuita de Azure SQL Database em assinaturas elegíveis. No portal, procure por **Azure SQL** e veja se aparece **Start free / Iniciar gratuitamente**.

Crie:

- Resource Group: algo como **nodo-dev**;
- Database: **nodo-dev**;
- Logical Server: um nome único, por exemplo **nodo-g4-dev**;
- região: escolha uma região próxima disponível;
- autenticação: registre com segurança o usuário administrativo criado.

Antes de confirmar, confira o resumo de custos.

Se a interface indicar custo diferente de zero e você não tiver certeza sobre os créditos da assinatura acadêmica, **não conclua a criação ainda**. Nesse caso, use um SQL Server compartilhado pelo grupo ou confirme qual assinatura estudantil está habilitada.

## 14. Liberar somente o seu IP

No Azure SQL:

1. abra o banco;
2. vá para o servidor lógico;
3. abra **Networking / Rede**;
4. selecione acesso público apenas por redes selecionadas;
5. adicione o IPv4 atual do seu Mac;
6. salve.

O Azure SQL usa a porta 1433.

Evite liberar o banco para qualquer endereço.

## 15. Conectar pelo editor

Se a extensão **SQL Server (mssql)** estiver disponível no Antigravity:

1. instale a extensão;
2. crie uma conexão;
3. informe o endereço do servidor, normalmente no formato:

~~~text
seu-servidor.database.windows.net
~~~

4. informe o banco **nodo-dev**;
5. informe usuário e senha;
6. teste a conexão.

Se a extensão não estiver disponível no Antigravity, você pode usar:

- Query Editor do próprio portal Azure;
- VS Code apenas como cliente SQL;
- outra ferramenta compatível com SQL Server no macOS.

O editor escolhido não muda o código ASP.NET.

# Fase 6: POC principal: Solicitar mentoria

## 21. Objetivo funcional

O estudante deve:

1. chegar à tela de agendamento com um mentor selecionado;
2. visualizar um horário disponível;
3. selecionar o horário;
4. informar o objetivo da mentoria;
5. confirmar;
6. criar uma Mentoria com status **Pendente**;
7. impedir que o mesmo slot seja reservado duas vezes;
8. voltar para o dashboard.

Para a POC, busca de mentor e autenticação podem estar simuladas.

## 22. Criar um ViewModel específico

Evite receber diretamente a entidade inteira da Mentoria pelo formulário.

Exemplo:

~~~csharp
public class SolicitarMentoriaViewModel
{
    public int DisponibilidadeId { get; set; }

    [Required]
    public string Descricao { get; set; } = string.Empty;
}
~~~

Depois, o Controller decide quais campos realmente podem entrar na entidade.

## 23. Action GET

A action GET deve:

1. receber ou localizar o mentor;
2. consultar os slots disponíveis;
3. montar a tela.

Estrutura conceitual:

~~~csharp
[HttpGet]
public async Task<IActionResult> Solicitar(int mentorId)
{
    var disponibilidades = await _context.Disponibilidades
        .Where(d => d.MentorId == mentorId && d.Disponivel)
        .OrderBy(d => d.Data)
        .ToListAsync();

    ViewBag.Disponibilidades = disponibilidades;

    return View();
}
~~~

Adapte os nomes às classes reais.

## 24. Action POST

A action POST deve fazer mais do que simplesmente inserir um registro.

Fluxo:

~~~text
receber DisponibilidadeId + Descricao
        ↓
validar formulário
        ↓
buscar slot no banco
        ↓
confirmar se ainda está disponível
        ↓
criar Mentoria Pendente
        ↓
marcar slot como indisponível
        ↓
SaveChanges
        ↓
redirecionar ao dashboard
~~~

Estrutura inicial:

~~~csharp
[HttpPost]
[ValidateAntiForgeryToken]
public async Task<IActionResult> Solicitar(SolicitarMentoriaViewModel model)
{
    if (!ModelState.IsValid)
        return View(model);

    var disponibilidade = await _context.Disponibilidades
        .SingleOrDefaultAsync(d =>
            d.Id == model.DisponibilidadeId &&
            d.Disponivel);

    if (disponibilidade == null)
    {
        ModelState.AddModelError(
            string.Empty,
            "Este horário não está mais disponível.");

        return View(model);
    }

    var mentoria = new Mentoria
    {
        Descricao = model.Descricao,
        Status = StatusMentoria.Pendente,
        DisponibilidadeId = disponibilidade.Id,

        // Temporário na POC:
        MentorandoId = ID_ESTUDANTE_POC,
        MentorId = disponibilidade.MentorId
    };

    disponibilidade.Disponivel = false;

    _context.Mentorias.Add(mentoria);

    await _context.SaveChangesAsync();

    return RedirectToAction("Dashboard", "Estudante");
}
~~~

## 25. Proteger contra reserva duplicada

O RNF-03 exige que duas pessoas não reservem simultaneamente o mesmo horário.

Só verificar **Disponivel == true** no C# reduz o problema, mas não é uma garantia completa contra concorrência.

A proteção final deve existir também no banco.

A modelagem atual indica que uma Disponibilidade pode ser usada no máximo por uma Mentoria. Portanto, o relacionamento no modelo físico deve impedir duas mentorias apontando para o mesmo slot.

Quando a estrutura final estiver pronta, teste explicitamente:

1. abrir o mesmo slot em duas abas;
2. confirmar na primeira;
3. tentar confirmar na segunda;
4. a segunda tentativa deve falhar de maneira controlada.

## 26. Montar a View

A View deve seguir a Tela 5 do Projeto de Interface.

Na primeira versão da POC, não precisa reproduzir cada detalhe visual do Figma. Precisa preservar a lógica:

~~~html
<form asp-action="Solicitar" method="post">
    <div>
        <!-- opções de horários -->
    </div>

    <div>
        <label asp-for="Descricao"></label>
        <textarea asp-for="Descricao"></textarea>
        <span asp-validation-for="Descricao"></span>
    </div>

    <button type="submit">Confirmar solicitação</button>
</form>
~~~

Depois integramos o CSS do projeto.

# Fase 7: Consultar histórico de mentorias

## 27. Objetivo funcional

O estudante deve consultar mentorias anteriores relacionadas à própria conta.

No dashboard, a documentação atual prevê histórico de sessões concluídas e acesso aos seus detalhes.

Para a POC, o histórico pode começar como uma View separada. Depois ela pode ser incorporada ao dashboard.

## 28. Consulta no Controller

A consulta deve filtrar pelo estudante.

Estrutura conceitual:

~~~csharp
public async Task<IActionResult> Historico()
{
    var mentorandoId = ID_ESTUDANTE_POC;

    var mentorias = await _context.Mentorias
        .Where(m =>
            m.MentorandoId == mentorandoId &&
            m.Status == StatusMentoria.Concluida)
        .Include(m => m.Avaliacao)
        .OrderByDescending(m => m.DataHora)
        .ToListAsync();

    return View(mentorias);
}
~~~

A propriedade **DataHora** deve ser substituída pelo campo que realmente representar a data da sessão no modelo final.

## 29. O que mostrar na View

Cada item do histórico deve permitir enxergar pelo menos:

- mentor;
- data e horário;
- status;
- descrição/objetivo;
- avaliação, caso já exista;
- ação para avaliar, caso a mentoria esteja concluída e ainda não tenha avaliação.

Esse último item conecta naturalmente o histórico ao caso de uso Avaliar mentoria.

# Fase 8: Avaliar mentoria

## 30. Regras

A avaliação deve:

- pertencer a uma Mentoria;
- ser feita pelo estudante daquela Mentoria;
- só existir após a Mentoria estar concluída;
- receber nota entre 1 e 5;
- aceitar comentário;
- existir no máximo uma vez por Mentoria.

## 31. ViewModel

~~~csharp
public class AvaliarMentoriaViewModel
{
    public int MentoriaId { get; set; }

    [Range(1, 5)]
    public int Nota { get; set; }

    public string? Comentario { get; set; }
}
~~~

## 32. GET da avaliação

Antes de abrir o formulário, valide:

1. a mentoria existe;
2. pertence ao estudante;
3. está concluída;
4. ainda não foi avaliada.

~~~csharp
[HttpGet]
public async Task<IActionResult> Avaliar(int mentoriaId)
{
    var mentoria = await _context.Mentorias
        .Include(m => m.Avaliacao)
        .SingleOrDefaultAsync(m => m.Id == mentoriaId);

    if (mentoria == null)
        return NotFound();

    if (mentoria.MentorandoId != ID_ESTUDANTE_POC)
        return Forbid();

    if (mentoria.Status != StatusMentoria.Concluida)
        return BadRequest();

    if (mentoria.Avaliacao != null)
        return BadRequest();

    return View(new AvaliarMentoriaViewModel
    {
        MentoriaId = mentoria.Id
    });
}
~~~

## 33. POST da avaliação

~~~csharp
[HttpPost]
[ValidateAntiForgeryToken]
public async Task<IActionResult> Avaliar(AvaliarMentoriaViewModel model)
{
    if (!ModelState.IsValid)
        return View(model);

    var mentoria = await _context.Mentorias
        .Include(m => m.Avaliacao)
        .SingleOrDefaultAsync(m => m.Id == model.MentoriaId);

    if (mentoria == null)
        return NotFound();

    if (mentoria.MentorandoId != ID_ESTUDANTE_POC)
        return Forbid();

    if (mentoria.Status != StatusMentoria.Concluida)
        return BadRequest();

    if (mentoria.Avaliacao != null)
    {
        ModelState.AddModelError(
            string.Empty,
            "Esta mentoria já foi avaliada.");

        return View(model);
    }

    var avaliacao = new Avaliacao
    {
        MentoriaId = mentoria.Id,
        Nota = model.Nota,
        Comentario = model.Comentario,
        Criacao = DateTime.UtcNow
    };

    _context.Avaliacoes.Add(avaliacao);
    await _context.SaveChangesAsync();

    return RedirectToAction(nameof(Historico));
}
~~~

## 34. Garantir unicidade no banco

A regra “uma avaliação por mentoria” também deve estar representada no banco.

Uma forma comum no EF Core é criar um índice único para a FK:

~~~csharp
modelBuilder.Entity<Avaliacao>()
    .HasIndex(a => a.MentoriaId)
    .IsUnique();
~~~

Adapte somente depois de conferir como o relacionamento está definido no DbContext do grupo.

- 1 mentoria concluída sem avaliação;
- 1 mentoria concluída já avaliada;
- opcionalmente 1 mentoria pendente.

Não use informações pessoais reais.

Exemplos de dados:

~~~text
Mentorando: Estudante POC
Mentor: Mentor POC
Descrição: Revisão de portfólio .NET
Status: Concluida
Nota: 5
Comentário: Sessão ajudou a definir próximos passos.
~~~

## 38. Mock temporário do usuário autenticado

Se a autenticação real ainda não tiver sido integrada, a POC pode usar um ID conhecido de usuário de teste.

Exemplo temporário:

~~~csharp
private const int ID_ESTUDANTE_POC = 1;
~~~

Marque claramente:

~~~csharp
// TODO: substituir pelo ID do usuário autenticado após integração do módulo de autenticação.
~~~

Esse código não deve permanecer como solução final.

# Fase 11: testar a POC

## 39. Teste de Solicitar mentoria

Cenário principal:

1. abrir a tela;
2. selecionar slot disponível;
3. preencher descrição;
4. confirmar;
5. verificar mensagem/redirecionamento;
6. consultar o banco;
7. conferir Mentoria criada como Pendente;
8. conferir slot marcado como indisponível.

Cenário de conflito:

1. tentar solicitar o mesmo slot novamente;
2. o sistema deve bloquear.

Cenário inválido:

1. enviar descrição obrigatória vazia;
2. o sistema deve mostrar validação;
3. nenhum registro deve ser criado.

## 40. Teste de Histórico

1. usar o estudante de teste;
2. abrir histórico;
3. confirmar que aparecem apenas mentorias daquele estudante;
4. confirmar ordenação;
5. confirmar que uma sessão de outro estudante não aparece.

## 41. Teste de Avaliação

1. abrir mentoria concluída;
2. registrar nota 1 a 5;
3. enviar comentário;
4. verificar gravação no banco;
5. tentar avaliar novamente;
6. o sistema deve bloquear;
7. tentar abrir avaliação de mentoria não concluída;
8. o sistema deve bloquear.

## 42. Consultar o banco

Com a extensão MSSQL ou Query Editor do Azure, use consultas simples para validar a persistência.

Exemplos:

~~~sql
SELECT * FROM Mentorias;
~~~

~~~sql
SELECT * FROM Avaliacoes;
~~~

Os nomes físicos podem variar conforme a configuração do Entity Framework.

# Fase 13: usar o Antigravity sem entregar o raciocínio ao agente

## 46. Tarefa boa para o agente

Em vez de pedir:

~~~text
faça o sistema de mentoria
~~~

use tarefas pequenas:

~~~text
Leia a documentação do NODO e a estrutura atual do projeto.

~~~

~~~text

- não implementar autenticação ainda;
- usar o mecanismo temporário de usuário POC já definido no projeto.
~~~

Esse tipo de prompt facilita revisar o que o agente fez e reduz alterações desnecessárias.

# Fase 14: preparar o vídeo individual da POC

## 47. O que precisa aparecer

Para uma POC baseada em Solicitar mentoria, o vídeo pode seguir esta sequência:

1. apresentar rapidamente que o caso de uso é **Solicitar mentoria**;
2. mostrar a aplicação rodando localmente;
3. abrir o fluxo de agendamento;
4. escolher horário;
5. preencher objetivo;
6. confirmar;
7. mostrar a solicitação criada;
8. mostrar no banco o registro persistido;
9. voltar ao código e mostrar rapidamente:
   - View;
   - Controller;
   - Model/ViewModel;
   - DbContext;
   - relação com SQL Server;
10. explicar o fluxo:
   **navegador → Controller → EF Core → SQL Server → resposta**.

A demonstração vale mais do que navegar por dezenas de arquivos.

## 48. Para a POC de Avaliar mentoria

O roteiro equivalente é:

1. abrir histórico;
2. escolher uma mentoria concluída;
3. abrir avaliação;
4. preencher nota e comentário;
5. salvar;
6. mostrar o registro no banco;
7. tentar avaliar novamente;
8. mostrar que o sistema impede uma segunda avaliação;
9. explicar View → Controller → EF → SQL Server.

# Fase 15: depois que a POC funcionar

## 49. Trocar mocks pelas dependências reais

Quando os outros módulos entrarem na main:

- substituir **ID_ESTUDANTE_POC** pelo usuário autenticado;
- substituir mentor de teste por dados reais;
- usar disponibilidades reais;
- integrar com Busca de Mentores;
- integrar ao Dashboard;
- remover seed de POC que não for necessário;
- revisar permissões e segurança.

## 50. Integrar as telas finais

Depois da regra funcionar, aproximar as Views dos wireframes:

- Tela 5: agendamento;
- Tela 6: dashboard do mentorando;
- histórico dentro do dashboard;
- avaliação aberta a partir de sessão concluída.

Não recomendo começar pela fidelidade visual. Primeiro feche persistência e regras do caso de uso.

## Pontos que ainda precisam ser confirmados no código do grupo

Este tutorial consegue orientar o trabalho com os documentos atuais, mas algumas decisões só podem ser fechadas quando o template de código da Etapa 03 estiver no repositório:

- versão exata do .NET;
- versão exata do Entity Framework Core;
- nome do DbContext;
- nomes finais das propriedades de Mentoria;
- forma definitiva de representar Mentor e Mentorando;
