## Parte I: Resumo executivo da reunião de acompanhamento

### 1. Mudança de orientação da POC: usar um caso de uso real do NODO

A orientação desta reunião altera, para o Grupo 4, a estratégia registrada no encontro de ==17/09/2026==. Embora a tarefa individual da POC tenha sido apresentada originalmente como a reprodução de um exemplo do microfundamento de Back-End, a professora afirmou considerar pouco produtivo repetir um exemplo genérico e recomendou aproveitar a atividade para desenvolver **um caso de uso real da própria aplicação do grupo**.

A recomendação foi direta: cada integrante deve escolher para a POC um caso de uso que **de fato assumirá no desenvolvimento do NODO**. A professora admite que a implementação possa precisar de refatoração ou correção posterior, mas entende isso como parte natural do desenvolvimento.

Para o planejamento do Grupo 4, portanto, a orientação mais recente é:

**POC individual → caso de uso real do NODO → responsabilidade futura do mesmo integrante.**

Essa orientação posterior deve prevalecer no planejamento do grupo, sem apagar o registro da orientação anterior.

### 2. Responsabilidade vertical por caso de uso

A divisão do trabalho não deve seguir uma especialização rígida por camada. A professora afastou a lógica em que uma pessoa fica apenas com Front-End e outra apenas com Back-End.

O integrante responsável por um caso de uso deverá acompanhar o fluxo de ponta a ponta:

- construir a interface relacionada ao caso de uso;
- implementar a lógica em ASP.NET / C#;
- salvar e recuperar os dados no banco;
- realizar os testes correspondentes;
- participar do registro e da demonstração da funcionalidade;
- manter a documentação do caso de uso coerente com a implementação.

O exemplo discutido foi a gestão de perfil/usuário: quem assumir esse caso de uso deverá cuidar da funcionalidade como uma unidade de entrega, atravessando interface, lógica e persistência.

### 3. Divisão entre Etapa 03 e Etapa 04 por complexidade

O grupo deverá separar os casos de uso entre as Etapas 03 e 04 considerando **complexidade**, e não simplesmente quantidade.

A professora sugeriu colocar os casos mais difíceis na Etapa 03. A justificativa é que, se esses casos apresentarem bugs ou exigirem mudanças, haverá maior margem de correção antes da entrega final.

Durante a reunião foram contados aproximadamente 24 elementos no diagrama, mas a própria professora alertou que alguns podem não representar casos de uso independentes. Foi citado como exemplo que **Cadastrar conta** e **Gerenciar perfil** talvez possam ser revistos ou agrupados.

A equipe deverá chegar ao próximo encontro com:

- casos de uso classificados entre Etapa 03 e Etapa 04;
- divisão aproximadamente equilibrada em termos de complexidade;
- responsável definido para cada caso de uso;
- representação visual dessa divisão no diagrama.

### 4. Dependências entre casos de uso e uso de mocks

A distribuição precisa considerar dependências. Se um caso de uso depende de outro ainda não implementado, há duas alternativas destacadas na reunião:

1. atribuir os casos dependentes ao mesmo integrante e desenvolvê-los na mesma etapa;
2. criar uma implementação simulada (*mock*) que represente temporariamente os dados ou o comportamento ainda inexistentes.

O objetivo é permitir que cada integrante avance com relativa independência sem ficar bloqueado pelo trabalho de outra pessoa.

### 5. Prazo real de implementação da Etapa 03

A professora reforçou que as três semanas da Etapa 03 não representam três semanas inteiras de programação. Uma semana deve ser preservada para testes e consolidação dos registros de teste.

Na prática, a equipe deve considerar aproximadamente **duas semanas para desenvolver os casos de uso da Etapa 03** e uma semana para testar, corrigir e documentar.

### 6. Requisitos técnicos para a POC e para a implementação

Para a POC, a equipe deve preparar o ambiente de desenvolvimento e avançar no microfundamento de Back-End. Foram citados:

- Visual Studio e SQL Server no ambiente Windows;
- Visual Studio Code para integrantes que utilizam Mac;
- implementação da lógica e das validações no Back-End em C#;
- persistência em SQL Server;
- JavaScript limitado principalmente às interações de interface, sem substituir a lógica de negócio e a validação do Back-End;
- abandono de soluções provisórias em JSON no Front-End como mecanismo principal de persistência.

A professora também reforçou que o padrão MVC adotado na disciplina deve ser seguido como estrutura acadêmica do projeto.

### 7. Coerência entre código e documentação

A documentação continua sendo tratada como dinâmica: requisitos, casos de uso, metodologia e demais artefatos podem mudar durante a implementação.

A exigência é que as mudanças sejam refletidas de forma coerente no GitHub. Se uma decisão de implementação alterar um caso de uso ou requisito, os artefatos relacionados também devem ser atualizados para evitar uma documentação fragmentada ou contraditória.

### 8. Entrega para o encontro de 29/09/2026

Para a orientação excepcional de terça-feira, ==29/09/2026==, a professora solicitou que o grupo avance em dois pontos:

- apresentar, quando possível, uma primeira POC;
- levar o diagrama de casos de uso já marcado com a divisão entre Etapa 03 e Etapa 04, discutida estrategicamente pelo grupo.

Também foi reforçada a necessidade de definir os responsáveis pelos casos de uso.

### 9. Testes da Etapa 03

A professora informou que tentaria recuperar, de uma turma anterior, um exemplo de documentação de testes para servir como referência. A partir da Etapa 03, a equipe deverá não apenas implementar as funcionalidades, mas também **registrar formalmente os testes realizados**.
