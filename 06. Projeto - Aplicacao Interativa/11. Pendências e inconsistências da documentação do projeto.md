# Pendências e inconsistências da documentação do projeto

> **Estado:** pendências identificadas durante a elaboração do Plano de Testes de Software. Esta nota serve como lista de revisão para alinhar a Especificação do Projeto, o Projeto de Interface e os artefatos técnicos do NODO antes da versão final.

## 1. Cancelamento de mentoria

**Documentos envolvidos:** Especificação do Projeto e Projeto de Interface.

O **RF-04** e os casos de uso de Gestão de Mentorias preveem que o mentor possa **cancelar uma mentoria previamente confirmada**, com atualização do status e geração de notificação.

No Projeto de Interface, o dashboard do mentor descreve as ações **Aceitar**, **Recusar**, **Adicionar horário**, **Adicionar material** e **Ver detalhes**, mas não define onde ou como ocorre o cancelamento de uma mentoria já confirmada.

### A resolver

- definir em qual tela o mentor cancela uma mentoria confirmada;
- definir o elemento de interface correspondente, por exemplo, botão `Cancelar mentoria`;
- definir se o cancelamento exige justificativa;
- definir o estado/status resultante;
- registrar a notificação enviada ao mentorando;
- atualizar o Projeto de Interface e, se necessário, os wireframes.

**Impacto no Plano de Testes:** o caso de teste de cancelamento de mentoria permanece com os passos pendentes até o fluxo ser documentado.

## 2. Alteração de senha do usuário autenticado

**Documentos envolvidos:** Especificação do Projeto e Projeto de Interface.

O **RF-13** determina que o usuário autenticado possa alterar sua própria senha informando a **senha atual** e uma **nova credencial**.

No Projeto de Interface, a tela de login documenta apenas o link **Esqueci minha senha**, relacionado ao fluxo de recuperação/redefinição de credenciais. Não há uma tela ou interação descrita para a alteração voluntária da senha por um usuário já autenticado.

### A resolver

- definir onde fica a gestão de credenciais do usuário autenticado;
- definir o fluxo `senha atual → nova senha → confirmação`;
- definir mensagens de erro e sucesso;
- diferenciar claramente **alterar senha** de **recuperar senha esquecida**;
- atualizar o Projeto de Interface e, se necessário, os wireframes.

**Impacto no Plano de Testes:** o caso de teste de alteração de senha permanece sem passos completos até a definição da interface.

## 3. Responsável pelo registro de anotações da mentoria

**Documentos envolvidos:** Especificação do Projeto, Projeto de Interface e modelagem da solução.

Há uma divergência sobre **quem registra as anotações da mentoria**:

- na Especificação do Projeto, em Gestão de Mentorias, o caso de uso **Registrar anotações da mentoria** está atribuído ao **Mentor**;
- no Projeto de Interface, o **dashboard do mentorando** apresenta o botão **+ Nova anotação**, descrito como registro de anotação privada de evolução/estudo;
- o modelo conceitual trata `ANOTACAO` como conteúdo associado à `MENTORIA`.

Essas descrições podem representar dois conceitos diferentes, mas isso ainda não está explicitado: **anotação privada do mentor sobre a evolução do mentorando** e **anotação pessoal do próprio mentorando**.

### A resolver

Escolher uma das alternativas:

1. **Apenas o mentor registra anotações da mentoria:** remover ou redefinir `+ Nova anotação` no dashboard do mentorando.
2. **Apenas o mentorando registra anotações pessoais:** atualizar o caso de uso e a descrição do RF-08.
3. **Ambos podem registrar anotações:** diferenciar os dois tipos no domínio e na interface, incluindo regras de visibilidade e privacidade.

Depois da decisão, revisar:

- RF-08;
- casos de uso;
- Projeto de Interface;
- diagrama de classes;
- Modelo ER / projeto da base de dados;
- Plano de Testes de Software.

**Impacto no Plano de Testes:** o ator e os passos do caso de teste de registro de anotação só podem ser fechados depois dessa decisão.
