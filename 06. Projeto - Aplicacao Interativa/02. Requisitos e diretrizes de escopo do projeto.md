## 1. Alinhamento Obrigatório com as ODS (Agenda 2030 da ONU)

Todo projeto desenvolvido no Eixo 2 **deve ter vínculo obrigatório** com pelo menos 1 dos **17 Objetivos de Desenvolvimento Sustentável (ODS)** da ONU ou seus sub-objetivos.

* **Conexão Prática:** O grupo deve escolher uma aplicação funcional interativa e mapear a justificativa do projeto com os sub-objetivos da Agenda 2030 (ex.: saúde e bem-estar, educação de qualidade, cidades sustentáveis, consumo responsável, etc.).

---

## 2. Requisitos Técnicos Obrigatórios e Stack Tecnológica (Eixo 2)

O Eixo 2 possui uma **stack tecnológica obrigatória** para a construção da Aplicação Interativa, integrando o Front-End, o Back-End e o Banco de Dados Relacional.

### 2.1 Back-End (Obrigatório)
* **Linguagem e Framework:** **C#** utilizando a plataforma **.NET / ASP.NET Core** (Web API RESTful ou ASP.NET MVC).
* **Mapeamento Objeto-Relacional (ORM):** **Entity Framework / Entity Framework Core** para persistência e manipulação dos dados.
* **Regras de Negócio:** Implementação modularizada dos controllers, services e repositórios em C#.

### 2.2 Front-End (Obrigatório)
* **Tecnologias Base:** **HTML5**, **CSS3** e **JavaScript (Vanilla JS)**.
* **Interatividade Web:** Construção da interface de usuário (*UI/UX*) com consumo de dados do Back-End via requisições assíncronas (Fetch API / Axios).

### 2.3 Banco de Dados Relacional (Obrigatório)
* **SGBD Relacional:** **SQL Server** (ou SGBD Relacional SQL padronizado no curso).
* **Modelagem de Dados:** Elaboração do Modelo Entidade-Relacionamento (MER) conceitual e implementação do esquema lógico de tabelas relacionais com chaves primárias (PK) e estrangeiras (FK).

### 2.4 Ferramentas e Padrões de Engenharia
* **Controle de Versão:** **Git & GitHub** (repositório institucional oficial da PUC Minas).
* **Modelagem UML:** Diagrama de Casos de Uso, Diagrama de Classes e Diagrama de Fluxo.
* **Metadados de Citação:** Inclusão obrigatória do arquivo de citação `citation.cff` na raiz do repositório.

## 3. Requisitos de Escopo do Software (Regra de Ouro)

### 3.1 Requisitos Funcionais (RF) e Estratégia de "Gordura de Segurança"
* **Mínimo Institucional:** 10 Requisitos Funcionais.
* **Estratégia Recomendada pela Profa. Rosilane:** Cadastrar **12 a 13 Requisitos Funcionais** na Etapa 1.
* **Justificativa Técnica:** 
 * Se o grupo enfrentar dificuldades de tempo ou complexidade técnica na fase de programação no meio do semestre, é muito mais simples **remover 2 requisitos** da lista do que adicionar novos.
 * A inclusão de um novo requisito no meio do projeto exige refazer o Modelo Entidade-Relacionamento (MER), alterar tabelas no banco de dados e reescrever código das classes em C#. A remoção de um requisito pré-existente não quebra a estrutura arquitetural já construída.

### 3.2 Funcionalidades Práticas Mínimas Exigidas
1. **3 CRUDs Completos:**
 * A aplicação deve conter pelo menos 3 módulos de CRUD (Create, Read, Update, Delete) para entidades principais do sistema (ex.: gerenciamento/cadastro, alteração, exclusão e listagem de usuários, produtos, agendamentos, etc.).
2. **2 Relatórios:**
 * **Relatório 1:** Relatório estruturado e consolidado com cruzamento de dados.
 * **Relatório 2 / Funcionalidade Específica:** Um relatório ou funcionalidade avançada que represente o valor central do tema de negócio escolhido pelo grupo.

### 3.3 Personas e Histórias de Usuário (User Stories)
* **Quantidade de Personas:** Obrigatoriamente **5 personas** bem definidas para o projeto.
* **Histórias de Usuário:** Obrigatoriamente **2 histórias de usuário** para cada persona (totalizando 10 histórias de usuário no projeto).

### 3.4 Requisitos Não-Funcionais (RNF) e Restrições
* Cadastrar com margem de segurança abrangendo aspectos de desempenho, segurança, usabilidade, regras de negócio e restrições de gestão.

## 4. Entregáveis por Etapa e Padrão de Envio

### 4.1 Documentação no GitHub
* Manter o repositório do GitHub sempre atualizado a cada etapa com o código-fonte C#/HTML/CSS/JS, diagramas (Casos de Uso, Classes, Fluxo, MER) e relatórios de testes.

### 4.2 Postagem no Canvas
Para cada etapa do cronograma (Etapas 01 a 05), o grupo deve postar:
1. Link atualizado do repositório no GitHub.
2. Projeto exportado do GitHub em formato `.zip`.
3. Relatório individual de participação e contribuição preenchido no formato `.pdf`.
4. Vídeos de apresentação (Etapa 01: vídeo de 3 min; Etapa 05: pitch comercial com demo de até 3 min).
