# Bancos de dados relacionais e SGBDs

SQL é uma linguagem usada para se comunicar com bancos de dados relacionais. Por isso, compreender SQL exige reconhecer primeiro a estrutura sobre a qual a linguagem atua: tabelas, colunas, linhas, chaves, relacionamentos e restrições. Esses elementos não existem isoladamente. Eles são organizados e administrados por um **Sistema Gerenciador de Banco de Dados**, ou SGBD.

Este artigo retoma conceitos já estudados em [[02. Modelagem de Dados/00. Modelagem de Dados - Resumo|Modelagem de Dados]], mas com outro foco. Na disciplina de Modelagem, a questão principal era como representar e estruturar os dados. Aqui, o objetivo é entender a estrutura que SQL encontrará quando começarmos a executar comandos sobre um banco real.

## O que é um banco de dados relacional

Um **banco de dados relacional** organiza os dados principalmente em **relações**, representadas na prática por tabelas. Cada tabela descreve algum tipo de objeto, evento ou associação relevante para o sistema.

Uma tabela de clientes, por exemplo, poderia ser representada assim:

| id_cliente | nome | cidade |
| --- | --- | --- |
| 1 | Ana | Belo Horizonte |
| 2 | Bruno | Contagem |
| 3 | Carla | Belo Horizonte |

Nesse exemplo, `Cliente` seria a tabela, cada coluna descreveria uma característica dos clientes e cada linha representaria uma ocorrência específica.

No vocabulário do modelo relacional, encontramos algumas correspondências importantes:

- **relação**: estrutura normalmente representada como tabela;
- **tupla**: uma linha da relação;
- **atributo**: uma coluna;
- **domínio**: conjunto de valores permitidos para determinado atributo.

Na prática cotidiana com SQL e ferramentas de banco de dados, é muito comum usar os termos **tabela**, **linha** e **coluna**. Os termos relação, tupla e atributo ajudam a compreender a base teórica do modelo relacional.

## Colunas, tipos de dados e domínios

As colunas não armazenam qualquer valor de maneira arbitrária. Cada coluna possui uma definição que determina o tipo de informação esperado.

Uma tabela poderia, por exemplo, ser criada conceitualmente com esta estrutura:

| Coluna | Tipo esperado |
| --- | --- |
| `id_cliente` | número inteiro |
| `nome` | texto |
| `data_nascimento` | data |
| `ativo` | valor lógico |

Esses **tipos de dados** ajudam o SGBD a interpretar, armazenar e validar os valores. Quando exploramos uma tabela em uma ferramenta gráfica, normalmente é possível visualizar não apenas os nomes das colunas, mas também seus tipos, tamanhos, possibilidade de receber valores nulos e outras propriedades.

O conceito de **domínio** é mais amplo que o tipo físico. Uma coluna `idade`, por exemplo, pode ter tipo inteiro, mas uma regra adicional pode determinar que somente valores positivos sejam válidos. O tipo informa a natureza geral do valor; as restrições podem refinar aquilo que é aceito pelo banco.

## Chaves e relacionamentos

O modelo relacional permite que informações distribuídas em tabelas diferentes sejam relacionadas. Para isso, são fundamentais as **chaves**.

Uma **chave primária** identifica de maneira única cada linha de uma tabela. Em uma tabela `Cliente`, por exemplo, `id_cliente` poderia desempenhar esse papel.

Uma **chave estrangeira** cria uma referência a uma chave existente em outra tabela. Considere uma tabela `Pedido`:

| id_pedido | data | id_cliente |
| --- | --- | --- |
| 101 | 2026-09-17 | 1 |
| 102 | 2026-09-17 | 3 |

A coluna `id_cliente` em `Pedido` pode ser uma chave estrangeira que referencia `Cliente.id_cliente`. Dessa forma, o banco consegue representar que cada pedido pertence a determinado cliente sem repetir todas as informações daquele cliente dentro da tabela de pedidos.

Essa estrutura será especialmente importante quando estudarmos consultas com `JOIN`, porque o SQL poderá combinar informações de tabelas relacionadas usando essas chaves.

## Restrições e integridade dos dados

Um banco relacional também utiliza **restrições**, ou *constraints*, para impedir estados considerados inválidos pelo modelo de dados.

Alguns exemplos comuns são:

- `PRIMARY KEY`: identifica unicamente os registros;
- `FOREIGN KEY`: estabelece referências entre tabelas;
- `NOT NULL`: impede que determinada coluna fique sem valor;
- `UNIQUE`: impede valores repetidos em uma coluna ou conjunto de colunas;
- `CHECK`: restringe os valores de acordo com determinada condição.

Essas regras ajudam a preservar a **integridade dos dados**. Em vez de depender apenas do programa que utiliza o banco, o próprio SGBD pode recusar operações que violem regras definidas em sua estrutura.

## Banco de dados e SGBD não são a mesma coisa

É útil separar dois conceitos que no uso cotidiano às vezes aparecem misturados.

O **banco de dados** é o conjunto organizado de dados e estruturas. O **SGBD** é o software responsável por criar, armazenar, consultar, alterar, proteger e administrar esses bancos.

PostgreSQL, MySQL e Microsoft SQL Server são exemplos de SGBDs relacionais. Cada um implementa SQL e fornece um mecanismo capaz de receber comandos, processá-los e acessar os dados armazenados.

Isso também significa que **SQL não é o banco de dados**. SQL é a linguagem. MySQL, PostgreSQL e SQL Server são sistemas que entendem essa linguagem, embora cada um possua seu próprio dialeto e recursos adicionais.

## Alguns SGBDs relacionais

### PostgreSQL

PostgreSQL é um SGBD relacional de código aberto amplamente utilizado. Pode ser instalado em diferentes sistemas operacionais e possui um conjunto extenso de recursos além do SQL padronizado.

### MySQL

MySQL é outro SGBD relacional bastante difundido. A **MySQL Community Edition** é a edição gratuita normalmente utilizada para aprendizagem, desenvolvimento e muitos projetos. Foi uma das opções recomendadas pelo professor para a disciplina.

### Microsoft SQL Server

Microsoft SQL Server é o SGBD relacional da Microsoft. Existem edições gratuitas voltadas a desenvolvimento e aprendizagem, além de edições comerciais. É importante separar duas questões: **licença** e **compatibilidade com o sistema operacional**.

As edições gratuitas permitem estudar e desenvolver sem adquirir uma licença comercial, dentro das condições de cada edição. Entretanto, o mecanismo do SQL Server não possui instalação nativa suportada para macOS. Em um Mac, é possível utilizar clientes gráficos para acessar uma instância de SQL Server executada em outro computador, máquina virtual ou serviço remoto. As imagens oficiais de contêiner do SQL Server são suportadas pela Microsoft em hosts Linux x86-64; ambientes de emulação ou tradução não são oficialmente suportados.

Para quem utiliza Mac com Apple Silicon, como os Macs com chips M1, M2, M3 e posteriores, essa diferença é especialmente importante: instalar um cliente de SQL Server no Mac é simples, mas isso não significa que o próprio servidor SQL Server esteja sendo executado nativamente naquele computador.

## O SGBD como serviço do sistema operacional

Um SGBD normalmente precisa permanecer disponível mesmo quando nenhuma interface gráfica está aberta. Por isso, o processo principal do servidor costuma funcionar **em segundo plano**, como um serviço do sistema operacional.

No Windows, serviços podem ser visualizados pela ferramenta de gerenciamento de serviços. Um SGBD instalado localmente pode aparecer com estados como `Running` ou `Stopped`. Quando está em execução, o servidor pode aceitar conexões dos programas clientes.

No macOS existe o mesmo conceito de processos e serviços executados em segundo plano, mas a administração não possui uma tela idêntica ao `services.msc` do Windows. Dependendo de como o SGBD foi instalado, é possível verificar seu estado por ferramentas do próprio fornecedor, pelo Monitor de Atividade, pelo `launchctl` ou, quando instalado pelo Homebrew, por comandos como:

```bash
brew services list
```

Portanto, a ideia é a mesma nos dois sistemas: existe um **processo servidor** que precisa estar ativo para receber conexões. O modo de visualizar e controlar esse processo muda conforme o sistema operacional e a forma de instalação.

## Arquitetura cliente-servidor

Uma forma útil de entender o funcionamento de um SGBD é separar **servidor** e **cliente**.

O servidor é o processo que gerencia os bancos de dados. O cliente é o programa usado pelo usuário ou por uma aplicação para enviar comandos ao servidor.

O fluxo pode ser resumido assim:

**usuário → cliente → SGBD → banco de dados**

O cliente envia uma instrução SQL. O SGBD interpreta a instrução, verifica permissões, escolhe uma estratégia de execução, acessa os dados e devolve o resultado ao cliente.

O servidor e o cliente podem estar no mesmo computador, mas isso não é obrigatório. Um programa em um notebook pode se conectar a um banco executado em outro servidor pela rede ou em um serviço de nuvem.

Essa distinção explica por que é possível utilizar DBeaver no macOS para acessar um SQL Server hospedado em uma máquina Windows ou Linux: o DBeaver é apenas o cliente dessa conexão.

## Acesso pela linha de comando

Muitos SGBDs oferecem clientes de linha de comando. No caso do MySQL, por exemplo, o comando `mysql` pode abrir uma sessão com o servidor.

Uma conexão pode solicitar informações como endereço do servidor, nome de usuário e senha. Quando a autenticação é aceita, o cliente passa a enviar comandos diretamente ao SGBD.

Um exemplo genérico de acesso ao MySQL local é:

```bash
mysql -u root -p
```

Nesse comando, `-u root` informa o usuário e `-p` solicita a senha. Depois da conexão, é possível executar instruções SQL dentro do terminal.

A linha de comando deixa especialmente clara a separação entre cliente e servidor: o programa `mysql` é um cliente; o processo do MySQL Server é o SGBD que recebe as requisições.

## Acesso por ferramentas gráficas

Também podemos acessar SGBDs por ferramentas gráficas. Elas costumam oferecer recursos para criar conexões, navegar pelos objetos do banco, visualizar tabelas e colunas, escrever consultas e examinar resultados.

Essas ferramentas são às vezes chamadas de **IDEs de banco de dados**, mas o termo mais preciso em muitos casos é **cliente gráfico** ou **ferramenta de gerenciamento de banco de dados**. Algumas possuem tantos recursos de desenvolvimento que funcionam, na prática, como uma IDE especializada.

Para criar uma conexão, normalmente precisamos informar alguns parâmetros:

- tipo de SGBD;
- endereço do servidor, ou *host*;
- porta;
- banco de dados ou esquema, quando necessário;
- usuário;
- senha;
- forma de autenticação.

Depois da conexão, a ferramenta costuma apresentar uma árvore de objetos. Dependendo do SGBD, podem aparecer bancos, esquemas, tabelas, *views*, índices e outros objetos. Ao expandir uma tabela, é possível visualizar colunas, tipos de dados, chaves e restrições.

## DBeaver

**DBeaver** é uma ferramenta gráfica de gerenciamento de bancos de dados que suporta diversos SGBDs. A edição Community é gratuita e de código aberto e possui versões para Windows, Linux e macOS, inclusive Apple Silicon.

Uma das vantagens para aprendizagem é utilizar praticamente a mesma interface para se conectar a bancos diferentes. Em vez de aprender imediatamente uma ferramenta específica para cada fornecedor, podemos criar conexões para MySQL, PostgreSQL, SQL Server e outros sistemas dentro do próprio DBeaver.

O DBeaver utiliza **drivers** para se comunicar com os diferentes SGBDs. Ao criar uma conexão, escolhemos o tipo de banco e informamos dados como host, porta, usuário e senha. Para MySQL, por exemplo, a porta padrão é `3306`; para SQL Server, a porta padrão é `1433`.

Depois da conexão, o navegador do banco permite explorar sua estrutura. Essa visualização será útil ao longo da disciplina porque conecta aquilo que vimos em Modelagem de Dados com a estrutura concreta existente no SGBD.

## Ferramentas para SQL Server

No Windows, a ferramenta tradicional da Microsoft para administração do SQL Server é o **SQL Server Management Studio, SSMS**. Ele não possui versão para macOS.

Para trabalhar com SQL Server a partir de macOS, existem alternativas multiplataforma. O **Visual Studio Code com a extensão oficial MSSQL** da Microsoft permite criar conexões e escrever consultas em T-SQL no Windows, macOS e Linux. O DBeaver também permite conectar-se ao SQL Server.

O Azure Data Studio apareceu durante anos em muitos cursos e tutoriais como opção multiplataforma, mas foi descontinuado pela Microsoft em fevereiro de 2026. Por isso, materiais antigos que recomendam Azure Data Studio devem ser interpretados nesse contexto.

## O que acontece quando abrimos uma tabela na ferramenta

Ao navegar por uma tabela em um cliente gráfico, estamos consultando os metadados mantidos pelo SGBD. A interface pode mostrar, por exemplo:

- nome de cada coluna;
- tipo de dado;
- tamanho ou precisão;
- possibilidade de valor nulo;
- chave primária;
- chaves estrangeiras;
- índices;
- valores padrão;
- demais restrições.

Essas informações descrevem a **estrutura** da tabela. Em outra área da ferramenta, podemos visualizar ou consultar os **dados** armazenados nela.

A distinção entre estrutura e conteúdo é importante para SQL. Comandos de DDL atuam principalmente sobre a estrutura; comandos de manipulação e consulta atuam sobre os dados existentes dentro dessa estrutura.

## Conexão com Modelagem de Dados

A sequência entre modelagem e manipulação pode ser entendida desta forma:

**modelo conceitual → modelo lógico relacional → implementação no SGBD → manipulação por SQL**

Na etapa de modelagem definimos quais entidades existem, quais atributos possuem e como se relacionam. Na implementação, essas decisões são traduzidas para tabelas, colunas, chaves e restrições. Depois disso, SQL permite criar, consultar e modificar essas estruturas e os dados nelas armazenados.

Por isso, ao olhar uma tabela no DBeaver ou em outra ferramenta, não estamos diante de algo diferente da modelagem estudada anteriormente. Estamos vendo sua implementação concreta em um SGBD.

## Pontos que costumam gerar confusão

- **Banco de dados e SGBD não são sinônimos.** O banco contém estruturas e dados; o SGBD é o software que os administra.
- **SQL também não é um SGBD.** SQL é a linguagem usada para dar instruções ao sistema.
- **DBeaver não é o servidor do banco.** Ele é um cliente que se conecta ao servidor.
- **Fechar o DBeaver não necessariamente desliga o banco.** Se o SGBD estiver instalado como serviço, ele pode continuar executando em segundo plano.
- **Ter SQL Server gratuito não significa conseguir instalá-lo nativamente em qualquer sistema operacional.** Licenciamento e compatibilidade são questões diferentes.
- **Uma ferramenta gráfica não elimina SQL.** Ela fornece uma interface para navegar e administrar o banco, mas as consultas continuam sendo expressas em SQL.
